# 8. System prompts, the Tools panel, approvals and Permission modes

Source: [Capability tiers and system prompts](https://github.com/qodesmith/unimatrix-zero/issues/9), [Workspaces](https://github.com/qodesmith/unimatrix-zero/issues/24), [Subagents in every Tree](https://github.com/qodesmith/unimatrix-zero/issues/32), [Provider drivers, process model and IPC event list](https://github.com/qodesmith/unimatrix-zero/issues/38), [Electron security posture](https://github.com/qodesmith/unimatrix-zero/issues/39) Q18, [ADR 0022](../../adr/0022-one-kind-of-tree-and-permission-modes.md), which supersedes #9's plain Trees, tiers and YOLO, [ADR 0023](../../adr/0023-three-kinds-of-setting-and-a-trees-own-permission-mode.md), which lets a Tree use its own Permission mode.

- **One kind of Tree.** Every Tree can read files anywhere on disk, write files and run commands, as far as the Permission mode allows, and web search, MCP servers, Skills and Subagents run as its Tools panel says. Every Tree has its own files ([§9](./09-the-trees-files.md)); there are no plain Trees and no Workspace to turn on, and the user never sees the word Workspace.
- **System prompt.** Set per Tree as a copy of the global default; changeable at any time, applying to later Replies with the re-read note. Each Reply records the exact text it ran under (an internal, read-only history). Presets ship read-only: **Default** (a plain helpful assistant, good with Markdown, no mention of agents), **Concise**, **Explain simply**, **Coding helper**; Duplicate makes an editable copy. The library in Settings holds presets, the user's own, and the global default; "Save to library…" in the Tree panel turns a variant into an entry. Deleting the current default falls back to the Default preset. Every Tree runs the vendors' own agent prompts (Claude's `claude_code` preset, Codex's base instructions) with the System prompt added after them, as T3 Code does ([ADR 0022](../../adr/0022-one-kind-of-tree-and-permission-modes.md)); Claude needs `snapshot: false` for a change to apply. Every Tree adds an app-written **files section** under the System prompt ([§9](./09-the-trees-files.md)).
- **What is never loaded** from the user's own setup: user-level `CLAUDE.md` / `AGENTS.md` and user settings (hooks, permissions, model, output style). What can be: the user's MCP servers, Skills and Plugins through the app's own libraries ([§17](./17-settings-and-themes.md)), and a linked folder's own `CLAUDE.md` / `AGENTS.md` and Skills. Claude runs with `settingSources: []` ([§20](./20-distribution-updates-and-vendor-programs.md)), which loads no `CLAUDE.md` at all, so the app reads the file at the linked folder's root itself and passes it to the session; parent folders are never read. Codex reads `AGENTS.md` on its own, so stopping its walk up through parent folders is a [§9](./09-the-trees-files.md) verify item. `.codex/config.toml` is never loaded. Plugin hooks never run.
- **The Tools panel** (per Tree, defaults in Settings → Tools): web search (always on by default), Subagents (on), each MCP server, Skill and Plugin from the libraries (on, except where noted), Claude account connectors (**off** by default: about 30k tokens per cold Turn), and the vendors' built-in Skills and Codex's remote plugins (off, listed in a "Built in" group per Provider). Tools switched off stay off in every Permission mode. Skills load on ChatGPT the way Codex loads them on its own, now that Codex can read files in every Tree; there is no app-owned `read_skill` tool ([§21](./21-architecture.md)). Toggles apply live with no visible resume dance. The Tools panel is part of the **Tree panel**, opened from the Tree menu, which also holds the Tree's System prompt, its own Permission mode and its "Always allow in this Tree" grants.
- **The libraries are content, not Settings** ([ADR 0023](../../adr/0023-three-kinds-of-setting-and-a-trees-own-permission-mode.md)). Editing or deleting an MCP server, Skill or Plugin entry reaches every Tree that uses it. Each entry has "On in new Trees" (on). An entry added later is on in new Trees and off in existing ones, and the toast that confirms the addition offers "Turn on in this Tree".
- **Skills from outside the libraries.**
  - **The vendors' default Skill folders** (`~/.claude/skills`, `~/.agents/skills`) are library folders the user adds with one click.
  - **Codex reads `~/.agents/skills` whatever its config folder is.** So the app rescans that folder at the start of every Codex thread and writes an off-rule for each Skill that isn't on in that Tree. A Skill that appears later in an added folder is off in existing Trees and on in new ones. A Skill found in two folders shows once in the Tools panel.
  - **A linked folder's own Skills** (`.agents/skills` and `.claude/skills`) load on both Providers from each Thread's working copy, rescanned whenever a thread starts. The Tools panel shows them as "From this folder", listing the selected Thread's Skills, or those of the Thread in the folder when no Thread is selected. Each switch is kept per Tree by Skill name, and a Skill that appears later is on. Parent folders' Skills are switched off.
- **The approval card** is inline in the Reply where the tool call happened; the stream pauses there. Allow once / Always allow in this Tree / Deny, and for anything outside the Tree's files, "This happens outside the conversation, so other Branches will see it too." It names the Subagent asking, if any. Once answered it collapses into a chip (✓ allowed / ✕ denied); in canvas mode a waiting Turn gets a badge. The app enforces this on both Providers (Claude `canUseTool` plus `PreToolUse`; Codex per-server `approval_mode` and approval requests). Which actions reach a card is the Permission mode's call (below); reads never do, and read-only MCP tools run without asking where the marker exists.
- **Reviewing additions.** A review screen appears only when an addition includes an MCP server with a local command: one screen per add action, listing `command` and `args`, Skill names, and what was dropped. Changed local-server definitions in a Plugin stay off with a "1 change to review" badge until accepted.
- **Permission modes.** A live AI Setting, modeled on T3 Code's, that replaces YOLO ([ADR 0022](../../adr/0022-one-kind-of-tree-and-permission-modes.md)). The global mode is set in Settings → Permissions ([§17](./17-settings-and-themes.md)). A Tree may use its own mode, set from the label beside the Input ([§6](./06-the-input-prompts-attachments-models.md)) or in its Tree panel; its **effective mode** is its own if it has one and the global mode otherwise ([ADR 0023](../../adr/0023-three-kinds-of-setting-and-a-trees-own-permission-mode.md)). No Prompt picks its own. A change applies from the Tree's next Reply: a streaming Reply keeps the mode it started with, since Codex fixes a Turn's approval settings when it starts, and Stop is the brake. Reads never ask in any mode, because Codex cannot restrict them and a read card would be a promise only Claude keeps.
  - **Full access** (the default): no approval cards and no Sandbox. Claude `permissionMode: 'bypassPermissions'` with `allowDangerouslySkipPermissions`; Codex `danger-full-access` with `approval_policy: never`. Nothing is protected, credentials included; the maintainer accepts that risk.
  - **Auto:** the vendor's own Reviewer decides, inside the Sandbox. Claude `permissionMode: 'auto'` with the Sandbox on: a model classifier approves or denies each call, and asks through `canUseTool` when it cannot decide. Codex `workspace-write`, approvals `on-request` and `approvalsReviewer: 'auto_review'`: a prompted subagent weighs the risk of each approval request (leaving the Sandbox, the network, MCP approvals, permission requests). Each review is one more model call, which uses the plan's limits and takes time.
  - **Auto-accept edits:** edits inside the Tree's files go ahead, and edits elsewhere get a card. Commands run inside the Sandbox without asking; leaving it gets a card ([§10](./10-the-sandbox.md)). Claude `acceptEdits` with sandboxed commands approved automatically; Codex `workspace-write` with approvals `on-request`, as [ADR 0018](../../adr/0018-commands-run-inside-the-vendor-sandbox.md) set them.
  - **Supervised:** every edit gets a card, and so does every command the vendor does not recognize as read-only; read-only ones (`ls`, `cat`, `grep` and the like) run without a card, as reads never ask. Commands run inside the Sandbox. Codex `workspace-write` with approvals `untrusted`, which runs its known-safe read-only commands and asks for the rest, as T3 Code's Supervised does; Claude `default` with the Sandbox's automatic approval of sandboxed commands off, leaving read-only commands to Claude's own handling.
  - "Always allow in this Tree" still covers trust in one Tree. The Tree panel lists those grants, and each one can be revoked.
- **A Tree's own mode.** The label beside the Input shows the Tree's effective mode, with "· this Tree" when the Tree has its own. Its menu acts on this Tree only: the four modes, and "Use the global mode (X)", with a check on the current choice, and it says "Applies to this Tree from its next Reply." Picking any mode, the global mode's own value included, gives the Tree its own mode, which stays put when the global mode changes. Settings → Permissions says how many Trees use their own mode, with a list linking to each Tree panel and "Reset all to global".
- **The narrowing prompt.** When the global mode narrows, a prompt lists every Tree whose own mode is not narrower than or equal to the new global mode. The order is partial: Full access is the widest and Supervised the narrowest, and Auto and Auto-accept edits each count as wider than the other, since neither contains the other. A change narrows when the new mode is not wider than or equal to the old one, so a move between Auto and Auto-accept edits narrows too. A change that only widens shows no prompt.
  - Each listed Tree has a checkbox, all ticked. "Switch these" removes the ticked Trees' own modes, so they follow the global mode.
  - "Keep their own modes", or closing the prompt, leaves them. The global change applies either way.
- **What the user sees under Auto.** The Reviewer's decision shows in the Reply, and the user cannot overrule it there. While it reviews, a "Reviewing…" line sits where the action happens. Approved: a collapsed "✓ approved by reviewer" chip, which expands to the action and the Reviewer's reason. Declined: a collapsed "✕ declined by reviewer" chip with the reason, and the AI carries on and adapts. There is no "Allow anyway": to push past a refusal, the user says so in the next Prompt or switches mode. A review that times out or fails counts as declined, with the reason "Reviewer didn't answer". When Claude's classifier cannot decide, the usual approval card appears, and its answer collapses into a chip like any card's.

## Verify while building

- What the vendors' agent prompts cost a cold first Turn on Claude, which re-read about 36k tokens of Claude Code's prompt and tool definitions in [#7](https://github.com/qodesmith/unimatrix-zero/issues/7), and how the re-read note counts it.
- Claude's `permissionMode: 'auto'` under subscription sign-in with `settingSources: []` (Agent SDK 0.3.307).
- Codex's `auto_review` through `app-server`: its `item/autoApprovalReview/*` notifications and their review payload (status, risk level, reason) are marked unstable in the protocol, so the chips may need to follow changes on a vendor bump.
- Which commands Claude runs without asking under `default` with the Sandbox's automatic approval off, and whether they match Supervised's read-only set.
- Whether `[[skills.config]]` off-rules passed through `config` on `thread/start`, `thread/resume` and `thread/fork` keep a Skill off in that thread alone. `skills/extraRoots/set` is app-server-wide, so the library folders and a linked folder's `.claude/skills` reach every Codex thread, and these rules are what keep each Tree to its own Skills. A fork that misses them leaks. `disabledPluginIds` on `turn/start` is not a way, since it "does not yet filter plugin capabilities".
- How far up from a Thread's working copy Codex's `repo` Skill scope reads `.agents/skills`, as with its `AGENTS.md` walk ([§9](./09-the-trees-files.md)).
- Whether Claude knows about the library Skills on a turn that starts with no tool call, since `verbatimPrompts` delivers skill listings only after a turn's first tool call ([provider dependencies](../../provider-dependencies.md), `verbatim-prompts`).
