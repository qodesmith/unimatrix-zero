# 16. Usage and limits

Source: [What usage data each Provider reports](https://github.com/qodesmith/unimatrix-zero/issues/35), [Usage and limit display](https://github.com/qodesmith/unimatrix-zero/issues/36) (prototype, variant D), [Reconnect, offline and error states](https://github.com/qodesmith/unimatrix-zero/issues/40) follow-up.

- **Where.** The sidebar's Usage section lists every window each Provider reports, named by length (5-hour, Daily, Weekly, Monthly), with freshness and ⟳ Refresh, and "No limits reported" where there are none; collapsed, its header shows one ring per Provider for its fullest window. A ring beside the Model pill in every Input shows the tightest window limiting the picked Model (per-model weeklies count only when that Model is picked) and from 80% spells it out ("82% of 5-hour · resets 6:20pm"). Settings → Connections shows every window with reset time and countdown.
- **Sources.** Claude: `rate_limit_event` per Turn (5-hour and 7-day in `unifiedWindows`) and the experimental on-demand `get_usage` on an open session, with per-model weeklies and the "On usage credits" state. Codex: `account/rateLimits/read` on demand and `account/rateLimits/updated` during Turns, with 0, 1 or 2 windows. If `get_usage` disappears, the app shows the last `rate_limit_event` ("From your last Reply, X ago") without per-model weeklies. ChatGPT credits are not shown in v1.
- **Refreshing.** The figures arrive with every Turn (Claude `rate_limit_event`, Codex `account/rateLimits/updated`), and that is the main source. Beyond that the app reads on demand. On Codex the host answers itself, so it reads when the host starts and on ⟳ Refresh. On Claude a read needs a session: a warm one when there is one, and otherwise one of the two sessions the app opens for a read ([§18](./18-offline-reconnect-and-error-states.md)): the read at connect, right after sign-in, and ⟳ Refresh with no open session, which opens an empty session for the read and closes it gracefully after 60 seconds idle, so it always outlives any token refresh it started; neither counts toward the limits it is reading. There is no timer, and no process started for a read may exit before a token refresh it began completes, because a `claude` process that quits mid-refresh can race over the refresh token and sign the user out ([Reconnect, offline and error states](https://github.com/qodesmith/unimatrix-zero/issues/40)); this replaces the 5-minute read in [Usage and limit display](https://github.com/qodesmith/unimatrix-zero/issues/36). Reset times are known, so countdowns run locally. After 10 minutes a figure is marked stale with its age; offline it says "Couldn't refresh · updated X ago".
- **Warning** at a fixed 80% on both, amber. **Limit reached:** the Input of every Model on that Provider becomes a card ("Claude's 5-hour limit is reached. It resets at 12:40pm (in 2 h 10 min). Your draft is kept.") offering **Continue with <a Model on the other Provider>**; the sidebar row turns red with "Back at 12:40pm". A refused Reply keeps its partial text with "Limit reached · back at 12:40pm" and **Retry with <other Provider's Model>**, then a plain Retry after the reset. Limits are per account, so every Thread on that Provider waits: a running Claude Reply that makes another request (tools, Subagents) is refused at that request and keeps its partial text, while Codex lets a running Turn finish. A refused request also brings the real figure back.

## Verify while building

- A real limit hit on either Provider; Codex windows on plans other than Plus ([#35](https://github.com/qodesmith/unimatrix-zero/issues/35)).
- Whether `get_usage` answers on a session that has carried no Turn ([#35](https://github.com/qodesmith/unimatrix-zero/issues/35), [#40](https://github.com/qodesmith/unimatrix-zero/issues/40)).
