# 6. The Input: Prompts, attachments, Models

Source: [Canvas mode UX](https://github.com/qodesmith/unimatrix-zero/issues/14), [Switching model and provider within a Tree](https://github.com/qodesmith/unimatrix-zero/issues/10), [Capability tiers and system prompts](https://github.com/qodesmith/unimatrix-zero/issues/9), [Settings and user preferences](https://github.com/qodesmith/unimatrix-zero/issues/22), [ADR 0022](../../adr/0022-one-kind-of-tree-and-permission-modes.md), [ADR 0023](../../adr/0023-three-kinds-of-setting-and-a-trees-own-permission-mode.md).

- **Where the Input is.** The Active Thread always shows its Input; every other Reply reveals one on hover, and a hover Input holding a draft stays until sent or cleared. A streaming Reply has an Input too, which takes a draft but sends only once the Reply finishes; sending a Prompt moves the focus to the new Reply's Input. An empty Tree shows one centered Input, a Turn wide, and the root Prompt it sends is drawn where the Input was. Submitting into a Reply that already has a response branches.
- **Send key** is a Setting: "Enter sends · Shift+Enter adds a new line" (default) or "Enter adds a new line · ⌘/Ctrl+Enter sends".
- **Model picker.** Every Input has one, defaulting to the Model of the Reply it is attached to; a new Tree starts from the last-used Model. Models are listed at runtime from each Provider. Models the current vendor program is too old for show disabled as "Needs an app update" (or "Update available"). A retired Model falls back to the Provider's current default, visibly. A signed-out Provider's Model offers "Sign in again" beside the picker ([§18](./18-offline-reconnect-and-error-states.md)); a removed Provider's Model falls back visibly too, until the Provider is connected again ([#22](https://github.com/qodesmith/unimatrix-zero/issues/22)). The Thread is never blocked and the Model never changes without the user seeing it.
- **Permission mode label.** Beside the Model picker, every Input shows its Tree's effective Permission mode as a small label, with "· this Tree" when the Tree uses its own mode. Clicking it opens a menu that acts on this Tree only: the four modes, and "Use the global mode (X)". It says "Applies to this Tree from its next Reply". The global mode is set in Settings → Permissions ([§8](./08-system-prompts-the-tools-panel-approvals-and-permission-modes.md), [ADR 0023](../../adr/0023-three-kinds-of-setting-and-a-trees-own-permission-mode.md)).
- **Switching Model or Provider** continues in the same Tree. Within a Provider, the session is kept. To another Provider, the Thread is handed over through one "rebuild session from Thread" path: ChatGPT takes real history through `thread/inject_items`; Claude takes a text replay in one user message. The full Thread is always sent, never cut or summarized. Replies written by another Model get a hidden `[Reply written by <Model>]` label and one app-written line in the System prompt explains it; the user never sees the labels. Thinking never carries over; tool calls and citations become plain text. Every Reply shows a Provider icon and a Model pill.
- **The re-read note.** One inline note above the Input (never a modal), shown only above about 20k tokens, for anything that re-reads the Thread cold: switching Provider, a System prompt change, an expired prompt cache, forking into a new working copy. Wording talks about the user's limit ("Switching to ChatGPT will re-read ~48k tokens of this conversation (uses more of your limit)."). The estimate is Context size, with the old Provider's setup overhead swapped for the new one's. A Setting hides the note.
- **Attachments.** An attach button plus paste and drop; any file type is accepted, and the option is never disabled. Limits follow T3 Code: up to 100 attachments per Prompt and 50 MiB per file; an image sent inline is shrunk to at most 2000 px on its long side and 10 MiB, with at most 80 MiB of images per Prompt, while the original is kept as attached. Images show as thumbnails with a lightbox; other files as chips (name, size). The Tree keeps a copy of every attachment as it was when sent, under `userData/attachments/` by SHA-256, at a path that ends in the file's own name and extension ([ADR 0001](../../adr/0001-app-owns-the-tree.md)), and the Prompt carries one line per attachment with its path (`[Attached file "x" is saved at: …]`), so the AI opens it with its own tools in every Tree and every Permission mode ([ADR 0022](../../adr/0022-one-kind-of-tree-and-permission-modes.md)). Attaching freezes the file at send time; naming a path in a Prompt reads the live file instead.
- **Inline as well, where the Model takes the type natively and it is cheap:** images on both Providers (Codex as `data:` URLs), PDFs on Claude, and UTF-8 text files up to 32 KB as text; a larger text file goes by path only. Every hand-over to another Provider sends each earlier Prompt's attachments the same way, from the copies, so losses never pile up.
- **A copy that can no longer be read.** The app never deletes a copy, but a user or a failing disk can. When an earlier Prompt's file can't be read, for any reason, the AI gets `[Attached file "x" can no longer be read]` in place of its path line and nothing inline, so a rebuild or a hand-over still goes through. An earlier image whose shrunk copy is gone but whose original reads goes by path only. That file's chip says "File missing" in place of its usual words; main checks the copies when a Tree opens and after each send. A file on the Prompt being sent that can't be read still fails the Reply ("Couldn’t read the attached file “x”"), and its chip says "File missing" too, so the user sees why. Claude's media budget still counts such a file at its recorded size.
- **Claude's media budget.** At most 20 MiB of base64 and 90 images and documents per request, counted over the whole Thread being sent: below `claude`'s own limits of about 24 MiB and 100, past which it drops the oldest without a word. Past the budget the oldest attachments go by path only; their path lines stay, so the AI can still open them. On a Claude Reply the Context size details drawer ([§5](./05-canvas-mode-and-chat-mode.md)) adds a line such as "Inline media: 14.2 / 20 MiB · 23 / 90 files" and how many earlier attachments now go by path only, and an earlier Prompt's attachment chip says "Sent by path only now" once its file has left the inline set. ChatGPT has no such budget ([ADR 0022](../../adr/0022-one-kind-of-tree-and-permission-modes.md)).
- **Extraction at attach time.** Office files (docx, xlsx, pptx, odt, ods, odp, rtf, epub, ipynb) are extracted to text; a PDF to its text per page plus a JPEG of each page with no text or with images over 10% of it, for at most 100 pages; past that the PDF gets text only, and the chip says so. Page images are 1600 px on their long side at about 85% quality, encoded by Chromium's canvas; no ffmpeg or other outside tool. JPEG, not PNG, because an image's tokens follow its pixel size (Claude: about width × height / 750), not its bytes, so the format cuts disk use and request bytes, which count against Claude's media budget, while the pixel cap sets the tokens. It runs in a hidden, sandboxed Chromium window with no Node, no file system and no network ([ADR 0014](../../adr/0014-electron-security-posture.md), amended), a new window for each job, since the renderer keeps its peak memory after one. Each job takes input up to 50 MiB, with 60 s per file and a cap on zip expansion, and main checks that each image is a JPEG within the expected dimensions; a failed job leaves the attachment with its path only. The extracted files sit beside the copy, are deleted with it, and their paths go in the Prompt beside the copy's, so a Model that can't read the original reads these.
- **The chip says what the Model can do with the file**, such as "ChatGPT will open this with its tools" or "Neither Model can play audio".
- **A folder dropped on the Input** becomes a chip holding its path, not a copy, that offers "Work in this folder" ([§9](./09-the-trees-files.md)).

## Verify while building

- The hidden extraction window on Windows, Linux and in a packaged build, which the spike ([#262](https://github.com/qodesmith/unimatrix-zero/issues/262#issuecomment-6950240100)) did not test.
- JPEG page image sizes against the spike's PNG sizes (scanned pages averaged 1.2 MB as PNG).
- The exact wording of each chip's line per type and Provider.
- Claude's exact limit weighting for cached tokens, which the re-read note's wording assumes ([#7](https://github.com/qodesmith/unimatrix-zero/issues/7)).
