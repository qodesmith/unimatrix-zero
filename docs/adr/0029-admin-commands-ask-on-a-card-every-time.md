# Admin commands ask on a card every time, and the password goes to `sudo` alone

The AI can't run a command that needs admin rights. Neither Provider's commands have a terminal, so `sudo` fails at once, and on the non-developer's path ([PRD §1](../prd/01-initial-release/01-product.md)) that shuts out fixing Wi-Fi, DNS or a printer. So the app lets the AI run an admin command once the user allows that one command on a card. On macOS and Linux the app points `SUDO_ASKPASS` at a helper of its own for every command the AI runs: when `sudo` calls the helper, the helper asks the app, and a card in the Reply names the command and asks for the password. On Windows the app's card comes first and UAC's own prompt second, and the app never sees a Windows password. The password passes through the app, and [ADR 0014](./0014-electron-security-posture.md) treats Reply content as hostile, so the threat here is a prompt-injected AI that runs commands to get the password or to run more as an administrator than the user allowed. Proposal: [#314](https://github.com/qodesmith/unimatrix-zero/issues/314). Findings: [#318](https://github.com/qodesmith/unimatrix-zero/issues/318) (macOS, Windows, and `sudo` in Docker) and [#322](https://github.com/qodesmith/unimatrix-zero/issues/322) (Linux, live on both Providers).

## Considered Options

- **The operating system's own password dialog**, opened by the helper. Rejected: it can't say which command or Tree is asking, it looks different on every system, and it trains people to type their password into any box that appears.
- **Piping the password to `sudo -S`.** Rejected: the AI would handle the password.
- **`sudoers` rules or Touch ID for `sudo`.** Rejected: both change system settings, which takes a terminal and an admin password, and that is not the non-developer's path.
- **The helper checks its own caller.** Rejected: the helper runs among the AI's commands, and under Full access the AI can run it, copy it or speak to the app in its place. The check belongs where the password is, in the app.
- **A per-session token as the guard against the AI.** Rejected as a guard: every command the AI runs can read it. It stays, for the one thing it does: other programs can't raise cards.
- **Leaning on each command asking again by itself.** Rejected: it holds today on both Providers on macOS and Linux, but only because each vendor program starts a command in a way neither vendor documents. The app runs `sudo -K` so that it holds whatever they do.
- **The app keeps the password until the command ends**, to answer a second ask from the same command itself. Rejected: it holds the password longer.
- **Reopening [ADR 0018](./0018-commands-run-inside-the-vendor-sandbox.md)'s Codex profile** so `sudo` runs under Supervised on macOS. Rejected for now: the profile's denied reads are what keep an allowed command inside the Sandbox there.
- **Windows: the AI's own command asks UAC.** Rejected: UAC comes up with nothing before it, names Windows PowerShell and shows only base64, so nothing tells the user which command they are allowing.
- **Windows' built-in `sudo`.** Rejected: it is off by default, an administrator has to turn it on, and in its default mode no output comes back.

## Consequences

- **The password is held only until it is handed to `sudo`.** It is never stored, logged, put in the Tree or a Snapshot, sent to a Provider, or included in a Report or Diagnostics. It stays in the app's memory from the card to the one `sudo` ask it answers, and is dropped then, or when the command ends without asking.
- **The app checks who is asking before it sends a password.** It confirms that the parent process of the helper that called in is the real system `sudo`, by its file path. This is what stops a fake `sudo` put first on the `PATH`, which the card would otherwise hand the password to. A command that runs the helper itself gets nothing.
- **What the guard can't stop.** The AI can still show a password dialog of its own making, outside the app. Other programs running as the same user stay out of scope, as in ADR 0014.
- **An Allow answers one password ask.** Nothing after the command the card names runs on that Allow, and the app runs `sudo -K` when an allowed command ends. The known cost: `sudo -K` also clears the password `sudo` remembers for the user's own Terminal.
- **The card may come up more than once for one command.** Inside one command `sudo` usually remembers, so `sudo a && sudo b` asks once. On ChatGPT on Linux the last `sudo` of such a command asked again. A wrong password brings the card back too, up to three times, before `sudo` gives up.
- **Deny is an ordinary failed command.** `sudo` ends at once and the AI sees its error.
- **An admin command asks every time, in every Permission mode.** "Always allow in this Tree" never covers the password ask. Auto and Auto-accept edits aren't built; the same rule holds for them.
- **Every admin command is a command that leaves the Sandbox.** Inside the Sandbox on macOS `sudo` never starts, on either Provider, so no helper is called and nothing is asked. ADR 0018's keychain rule doesn't stand in the way: its deny list keeps a command inside the Sandbox from reading keychain files, and `sudo` reads none; it checks the password through the system.
- **Full access: admin commands work on both Providers**, on macOS and Linux through the card and the password, on Windows through the card and UAC.
- **Claude under Supervised on macOS: one card.** An admin command already needs the card that lets it run on the whole computer, and the password field goes on that card. The app then holds the password until that command's `sudo` asks, which is longer than under Full access, where the card comes up only once `sudo` has asked. Nobody has built or tested this; [#320](https://github.com/qodesmith/unimatrix-zero/issues/320) has to prove it.
- **ChatGPT under Supervised on macOS: not supported for now.** `sudo` is refused even after the user lets the command out of the Sandbox, because a let-out command there runs in a new Sandbox that keeps the denied folders (ADR 0018). The user is told plainly to switch the Tree to Full access.
- **Linux follows macOS**, confirmed live on Ubuntu 24.04 on both Providers. Three things differ:
  - **Plain `sudo` calls the helper**, with no `-A`. On macOS the AI has to write `sudo -A`, so the System prompt tells the AI to. So this decision covers any `sudo` that reaches the helper.
  - **A `sudo` that can't use the helper gets a plain message.** Ubuntu 25.10's has no `-A`.
  - **The app turns on no Sandbox on Linux yet**, on either Provider: ADR 0018's Linux part isn't built (#322). So Supervised gives two cards: the ordinary command card, then the password card. Accepted until the Linux Sandbox is built. What an admin command does inside that Sandbox is answered then; [#324](https://github.com/qodesmith/unimatrix-zero/issues/324) holds the rerun.
- **Windows: the app's card, then UAC.** The AI's command asks the app, the card names the command, and only after Allow does anything ask UAC. The card has to carry the meaning, since UAC's text can't be set. Each admin command brings UAC again: Windows keeps no memory of a Yes.
  - **A signed helper of our own does the elevating**, so UAC names our app, and the command's output comes back over the app's own channel. Nobody has tested a helper of our own; #320 has to prove it. _Contradicts [ADR 0006](./0006-unsigned-distribution.md), which ships Windows unsigned with no paid signing: [ADR 0028](./0028-the-windows-git-exe-is-written-in-go.md) ships the app's `git.exe` unsigned for the same reason. An unsigned helper would show in UAC under an unknown publisher (expected, not tested). Open: the maintainer settles which of the two gives way before #320 builds the helper._
  - **One admin command at a time.** Two UAC prompts look the same, so the app queues admin commands: each card and the UAC prompt it leads to finish before the next card can be answered.
  - **Under the Sandbox modes on Windows: not decided here.** The app turns on no Sandbox on Windows yet, on either Provider, and Claude has none there (ADR 0018). With Codex's Sandbox on, a command inside it could neither bring up UAC nor reach the app, so an admin command has to leave the Sandbox, as on macOS; a command let out of it did reach UAC (#318). How many cards a Supervised user gets before UAC is settled when #320 builds it.
  - **The command may run as another account.** For a standard user it runs as the administrator whose password UAC took, and with administrator protection on, as a separate hidden account. A command that touches "my" files or settings then touches that account's. The card says so, and the app doesn't block it.
- **Why `sudo` gets a password helper when the app's own `git` gets none** ([ADR 0027](./0027-the-apps-git-never-asks-for-a-login.md)). The app's `git` has no login to give and would have to keep one, a password program of the user's desktop would open with no warning, and the person who pushes is a developer with a `git` of their own. Here the password is one the user already knows, the app keeps nothing, the helper is the app's own and its card names the command, and the user it serves has no other way. `SUDO_ASKPASS` is read by `sudo` alone, so ADR 0027's settings for `git` and `ssh` stand as they are.
- **Provider dependencies.** The helper is reached only while both vendor programs pass `SUDO_ASKPASS` and the app's token on to the commands they run, the route `DEVELOPER_DIR` already takes. `sudo -K` covers every command that starts after an allowed one ends. While the allowed one still runs, another command is kept from its remembered password only by how each vendor program starts commands.
