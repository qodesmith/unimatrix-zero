# The app keeps its own copy of Provider session data

After each Reply the app saves the Provider's raw session data into its own SQLite database as opaque blobs, so any Provider session can be restored exactly, however old the Tree. Providers delete their copies (Claude after `cleanupPeriodDays`, which has no "never" and is enforced by the user's own `claude` sharing `~/.claude`), and the alternative, rebuilding by text replay, re-sends the whole Thread and loses reasoning and tool state. For Claude the Agent SDK's `sessionStore` (alpha, SDK version pinned) writes transcript entries to our store and resumes from a temporary folder, and the app also copies `tool-results/` and `subagents/`; if the store API breaks, writing the transcript file back is the verified fallback. For Codex the app keeps each `rollout-*.jsonl` (possibly `.zst`) and every ancestor a fork points into, and writes it back under its original name before `thread/resume`. Both formats are internal to the Providers, so they are never parsed or edited. Findings: [Tree storage and source of truth](https://github.com/qodesmith/unimatrix-zero/issues/11).

## Consequences

- Resume order: exact restore (silent), then Codex `thread/inject_items` from saved items, then text replay. Only the last two are shown to the user.
- Deleting stored session data is the app's job: a session goes when no Reply references it and, for Codex, no descendant fork still points into it.
- Roughly 10 KB per Turn of extra disk; no cap in v1.
- Signing in as a different account keeps Trees working; Claude may re-think instead of reusing earlier thinking.
- **Amended: deleting Turns rewinds the Provider session to match the Tree.** Without this, a Provider session still holds deleted Turns and the AI remembers them on the next Prompt from the new leaf. Codex: `thread/revert { threadId, beforeTurnId }` when the deletion is confirmed. Claude: `resumeSessionAt` on the next continue, which is how its rewind works. If the Codex program isn't available (ChatGPT disconnected, or it fails to start), deletion still goes ahead; before the next Prompt from a leaf, the app checks whether the session goes further than that leaf, and anything further can only be deleted Turns, so it rewinds then. Branching still forks (ADR 0001) and never rewinds. Use archived on restore ([ADR 0011](0011-archives-are-their-own-versioned-format.md)) counts as a deletion. Verified in the build: `thread/revert` writes a new rollout for the thread that refers back into the old one and leaves the old file untouched, so forks that point into it keep working; the app keeps both files ([#72](https://github.com/qodesmith/unimatrix-zero/issues/72)). Findings: [Exporting and restoring Trees](https://github.com/qodesmith/unimatrix-zero/issues/27).
- **Amended: Claude's entries are read for two fields, as the SDK's store needs.** The SDK's `sessionStore` treats each entry's `uuid` as its idempotency key, so the app skips an entry whose `uuid` it already keeps. The write-back fallback files entries by `type` as the SDK's own write-back does: a Subagent's `agent_metadata` entries are left out of its `.jsonl`, and the last one, without `type`, becomes its `.meta.json`. Nothing else in an entry is read, and what is kept is never edited. Findings: [Claude driver](https://github.com/qodesmith/unimatrix-zero/issues/66).
- **Amended: a Reply the app quit in keeps its Prompt in the Provider session.** The app saves Codex's rollout only when a Reply is recorded, so an interrupted Reply's turn is on disk but not in the app's copy. Writing the copy back before `thread/resume` leaves alone a rollout on disk that starts with the copy's bytes, since that is the same rollout carried further; anything else is written over as before. A Retry's rewind on a Provider session Codex hasn't loaded still writes the copy over it, because that write-back is the rewind. Claude's `sessionStore` is flushed `eager`, so each entry reaches the app as `claude` writes it rather than at the result, and the interrupted Prompt is in the app's copy when the session resumes. Neither format is parsed: the Codex check compares bytes. The text the Reply had shown is not added to either Provider session, since that would mean writing in the Provider's own format, so the AI remembers only the Prompt. Findings: [#143](https://github.com/qodesmith/unimatrix-zero/issues/143), [#149](https://github.com/qodesmith/unimatrix-zero/issues/149).
- **Amended: a Retry after a Reply cut short drops only the failed turn.** That Reply left its Prompt in the Provider session but was never saved, so a rewind to the Reply before it would drop the Prompt too. Instead, as soon as a Provider session holds a Prompt, the app records that Prompt's place in it, whether or not the Reply finishes. Claude: the app gives each Prompt its own `uuid`, and records it once the app's copy holds that entry; a Retry resumes with `resumeSessionAt` on the cut-short Reply's Prompt, so that Prompt and the retried one reach the AI as one user turn. Codex: the turn id `turn/start` returns; a Retry keeps the rollout on disk, since it holds the cut-short turn, and calls `thread/revert` before the failed turn, loaded or not. After any revert, the app saves the old rollout again from disk: the new rollout points into it, maybe past the app's copy, and a resume from a copy that ends too soon fails. The failed turn's place stays recorded until Codex reports the revert, so a Retry that fails before it still cuts the next time; Codex keeps a revert on disk, so a retry after one doesn't revert again. Without a recorded place, the Retry goes on as before. Findings: [#151](https://github.com/qodesmith/unimatrix-zero/issues/151), [#153](https://github.com/qodesmith/unimatrix-zero/issues/153).
