# No AI library: drive the Provider SDKs directly

The app talks to Providers through the Claude Agent SDK and its own thin JSON-RPC client for `codex app-server` (types generated by `codex app-server generate-ts`, pinned to one Codex version), both mapped into one small Turn/Reply event union and sent over a single typed Electron IPC channel. With a CLI-backed Provider the CLI already owns the tool loop, history and permissions, so an AI library would only add a stream format and a `useChat` that assumes one linear conversation; the hard parts (Forks, concurrent Threads, native session forking, `canUseTool`, rate-limit events, interrupts) we'd write ourselves either way. T3 Code does the same.

## Considered Options

- **TanStack AI.** Rejected: RC with heavy churn; its Claude adapter spawns `claude` directly and loses fork and usage events; its Codex adapter wraps `codex exec`, which streams no text and supports no approvals.
- **Vercel AI SDK.** Rejected: relies on third-party providers pinned to SDK versions, models one linear chat, and doesn't connect tool approval to the CLIs' permissions.
- **`@openai/codex-sdk` for ChatGPT.** Rejected: runs `codex exec` per Turn, so Replies arrive whole instead of streaming, and approvals are auto-rejected.

## Consequences

- Event names borrow the AG-UI vocabulary, so `@tanstack/ai-client` can be plugged in later without a rewrite.
- Streaming Replies live in a separate store keyed by Reply id (TanStack Store) alongside TanStack Query for saved data, so only the Turn being written re-renders.
- AI Elements and the shadcn AI helpers are unusable (typed against the libraries above); the UI uses the library-agnostic shadcn components and Streamdown.
