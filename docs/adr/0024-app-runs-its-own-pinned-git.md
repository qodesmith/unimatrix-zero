# The app runs its own pinned `git`, never the user's

Every Snapshot runs `git`, and nothing said where that `git` came from. Run from `PATH`, it is often missing or broken. A Mac app started from the Dock finds only `/usr/bin/git`, which without the Command Line Tools is a stub that fails and opens Apple's "install developer tools" dialog. Windows ships no `git`, and Linux usually has one, but not always. Where it is present, it is whatever version the user has, while the isolation flags from [ADR 0014](./0014-electron-security-posture.md) were tested on one. So `git` becomes a vendor program: the app downloads a pinned, portable build into `userData`, the way [ADR 0008](./0008-app-managed-vendor-programs.md) downloads `claude` and Codex, and runs it by its full path. Findings: [#275](https://github.com/qodesmith/unimatrix-zero/issues/275).

## Considered Options

- **The user's `git` from `PATH`, and asking them to install it when it is missing** (T3 Code's approach). Rejected for the reasons ADR 0008 gave for the vendor programs: most of our users aren't developers, and an unknown version breaks quietly.
- **Building `git` ourselves.** Rejected: GitHub Desktop's [dugite-native](https://github.com/desktop/dugite-native) already publishes portable builds for every platform the app ships on, each with a published sha256, and GitHub Desktop runs them for millions of users.

## Consequences

- **The builds are dugite-native's release archives**, the `.tar.gz` per platform, downloaded from its GitHub release, unmodified. The manifest names each with its sha256, beside `claude` and Codex. The download is checked before it is unpacked, and the whole folder is kept: Windows `git` needs its `cmd`, `ucrt64`, `usr` and `etc` folders, and the Mac and Linux builds keep their sub-programs in `libexec/git-core` as links to `git`. The archives also hold Git LFS and Git Credential Manager, which the app never runs. They are kept anyway, since a build is never modified. Unpacked, a build is about 110 to 160 MB.
- **`git` is GPLv2.** The app downloads from dugite-native's own release, so dugite-native is the distributor. If we ever host the archives ourselves, we have to offer the source too.
- **Signatures:** the Windows `git.exe` carries Git for Windows' Authenticode signature. The Mac `git` is only ad-hoc signed, not notarized, and it runs because downloads made by the app carry no quarantine flag (ADR 0008). Linux builds need glibc 2.34 or newer.
- **Downloaded at launch, not on Connect.** Every Tree takes Snapshots whatever its Provider, and the build is small enough that it is usually in place before the first Reply. Until it is in place (still downloading, or the download failed), a Reply finishes with no Snapshot, recorded as failed, and the user is told once per launch that file history starts once the download finishes. The next Reply that follows one without a Snapshot takes it first. A failed download is tried again the next time a Snapshot waits for it.
- **The app's own `git` never looks on `PATH`.** The dugite builds for Mac and Linux are built for `/`, so they would look for their sub-programs there and then on `PATH`. The app tells them where theirs are, the way GitHub Desktop does. Windows `git` finds its own. The commands a Tree's AI runs still find `git` themselves; on a Mac with no developer tools they reach the app's own ([ADR 0025](./0025-a-developer-folder-for-a-mac-with-no-developer-tools.md)).
- **Hooks are looked for inside the program file itself.** Windows `git` reads `/dev/null` as an empty file, but `core.hooksPath=/dev/null` becomes the folder `\dev\null\` on the drive, which any user can create. A file can't hold a hook on any platform.
- **New versions arrive with app bundles**, as `claude`'s and Codex's do, and the weekly vendor bump moves the pin too. A `git` bump skips the Provider checks gate: CI's unit tests already run the isolation tests against the new build on Mac arm64 and x64, Windows x64 and Linux x64.
