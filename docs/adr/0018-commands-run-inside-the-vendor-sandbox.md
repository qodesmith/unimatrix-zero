# Commands run inside the vendor Sandbox, set the way the vendor's desktop app sets it; YOLO removes it

The approval card decides whether a command runs; nothing decided what an approved command can reach. Once allowed, a command runs as the user, with `~/.ssh`, `~/.aws`, `~/.config/gh` and the open internet, and a prompt injection in a README or a confused Model can make a harmless-looking command carry any of that out. Both vendor programs ship an operating-system Sandbox for exactly this (Seatbelt on macOS, bubblewrap on Linux), and both vendors' own desktop apps turn it on by default and ask only when a command wants out; fewer prompts and a Sandbox are the same decision. We do the same: every command in a Write files + run commands Workspace runs inside the vendor's Sandbox, configured to what that vendor's desktop app does, and YOLO removes it for people who, like a developer running `claude --dangerously-skip-permissions`, take that risk themselves. Nothing happens unless we do it: [ADR 0008](./0008-app-managed-vendor-programs.md) isolates our vendor copies from any user config, and Claude's Sandbox is off until the app turns it on. T3 Code never turns it on for Claude. Findings: [Vendor sandboxing for commands the AI runs](https://github.com/qodesmith/unimatrix-zero/issues/49), with the fact-finding in [vendor-sandboxing.md](https://github.com/qodesmith/unimatrix-zero/blob/research/vendor-sandboxing/docs/research/vendor-sandboxing.md). Live tests: [#53](https://github.com/qodesmith/unimatrix-zero/issues/53), with the results in [sandbox-live-tests.md](https://github.com/qodesmith/unimatrix-zero/blob/research/sandbox-live-tests/docs/research/sandbox-live-tests.md); the four edges they corrected are marked below.

## Considered Options

- **Approvals only, no Sandbox** (what T3 Code does for Claude, and both vendors in its default Full access mode). Rejected: the card judges intent from one line the AI wrote, in a few seconds. It cannot judge reach.
- **The Sandbox as a reason to approve less.** Rejected: both Sandboxes cover shell commands only; file tools, web fetch, MCP servers and hooks run outside them, Codex never restricts reads, and native Windows has none. A user who approves on the strength of the Sandbox accepts exposures they cannot see. The tiers and cards from [#9](https://github.com/qodesmith/unimatrix-zero/issues/9) and [#24](https://github.com/qodesmith/unimatrix-zero/issues/24) stand unchanged; the Sandbox is the floor under them.
- **Folder-only reads, as Cowork does.** Rejected: Cowork runs Claude in a Linux VM with its own toolchain, so hiding everything outside the attached folder costs nothing. We run on the user's machine with the user's node, bun and brew, so commands must read outside the working copy or nothing builds. Codex cannot restrict reads anyway.
- **Keeping the Sandbox on under YOLO**, as a second switch. Rejected: YOLO is the developer's `cc` alias, and two switches is the nuance this decision exists to remove. #9's rule that YOLO "never widens what a Tree can do" was about tools and tiers and still holds: tools that are off stay off, write-only stays write-only, plain Trees stay plain.
- **Refusing run commands where the Sandbox is unavailable.** Rejected: worse than the desktop apps for every Windows user. The user chose run commands; they are told once instead.

## Consequences

- **Codex: ChatGPT desktop's defaults, as-is.** `workspace-write` with network off and approvals `on-request`, reviewed by the user. Writable roots are the working copy and the temp folders; reads are the whole disk, because Codex has no deny-read outside experimental profiles. A command that needs more asks up front (`require_escalated`), which arrives as an approval request and becomes the card below. `danger-full-access` with `approval_policy: never` exists only under YOLO.
- **Claude: Cowork's intent through the SDK Sandbox.** `Options.sandbox` with `enabled`, writes allowed only in the working copy and temp, and a credentials deny list (`~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.kube`, `~/.gnupg`, keychains, and the Provider folders in our own `userData`) mirrored as `Read(...)` deny rules so the Read tool is covered too, which the SDK merges into the Sandbox's own list. Network is default-deny with an empty allowlist. `allowUnsandboxedCommands` stays true so the hatch below exists; `failIfUnavailable` is false, and since the SDK reports availability only as a line on stderr, the app probes before the session (below). Because it rides the `--settings` layer it works with `settingSources: []`, and a linked folder's `.claude/settings.json` cannot loosen it.
- **Reads are the whole disk minus credentials, on both.** That is the one place we differ from Cowork, for the reason above, and it matches what the vendor CLIs do.
- **Asking at the fence is one card.** When the Sandbox blocks a command (a path, the network), the Model asks to run it outside: Claude's `dangerouslyDisableSandbox` retry reaches `canUseTool`, Codex's escalation arrives as `requestApproval`. Both become an approval card that says the command would run outside the Sandbox. "Always allow this command in this Tree" given on that card covers only the outside-the-Sandbox form of that command, and a plain always-allow never covers it. That last clause is not an SDK property but something the app builds (verified live in #53): a `Bash(...)` allow rule, from `permissions.allow` or `allowedTools`, approves the retry with no callback, so every Bash allow rule the app writes is accompanied in the same app-owned `settings` block by the ask rule `Bash(dangerouslyDisableSandbox:true)`, which takes precedence and brings the retry back to `canUseTool`. `bypassPermissions` lets the Model leave silently too, and is never in force outside YOLO. Claude has a second trigger at the fence: a blocked connection arrives as `canUseTool` with `toolName: "SandboxNetworkAccess"` and the host, with a suggested per-host `WebFetch(domain:…)` rule; approving it opens that host and keeps the command inside the Sandbox. What each of the two cards says and what "Always allow" does on each is [#56](https://github.com/qodesmith/unimatrix-zero/issues/56).
- **Network is closed by default on both**, as in the desktop apps; a command that needs it goes through the card, and "Always allow" keeps `bun add` from asking twice. No built-in allowlist in v1: if the card fires too often for registries, a short allowlist is a follow-up, not a change of rule; whether the SDK's per-host suggestion changes that, and which package-manager caches must be writable for `bun add` to reach the network at all (with only the working copy and temp writable it fails on `~/.bun` first, on both vendors), are in [#56](https://github.com/qodesmith/unimatrix-zero/issues/56). The per-Workspace Setup command from [ADR 0010](./0010-linked-folder-holds-one-thread.md) is the user's own command, not the AI's, and runs outside the Sandbox. MCP servers and web search run outside the Sandbox on both vendors and keep their own approvals from #9.
- **Other Branches' working copies and the hidden store** are on the deny list on both vendors, so #24's hard deny is enforced by the operating system rather than by a hook, except under YOLO where the hook and the auto-declined approval are all that remain.
- **Subagents** run inside the parent's Sandbox on both vendors; there is no per-Subagent setting.
- **Linux: the app ships bubblewrap and socat** as app-managed helpers downloaded beside the vendor programs, hashed in the manifest, and placed first on Claude's `PATH` through `Options.env`; `bwrapPath` and `socatPath` are honoured only from the root-owned managed settings file, which the app cannot write (verified live in #53). The shipped socat is static or carries its libraries, and bwrap is the real binary, not a wrapper. Codex brings its own. Amends ADR 0008. Where unprivileged user namespaces are blocked (Ubuntu 24.04's AppArmor default) the Sandbox is unavailable, below.
- **Where the Sandbox is unavailable, commands still run and the user is told once.** Native Windows on both vendors (Claude has no Windows Sandbox outside WSL2; Codex's native one is new, off by default, and not turned on in v1), and Linux where bubblewrap cannot run. Turning on run commands in such a Tree shows a one-time notice that commands here run without the Sandbox, and the Tools panel says so while it is on. Never silently, which is what Codex does on its own when its Windows Sandbox is off. Neither vendor detects "present but cannot run": where user namespaces are blocked, both start normally and then every command fails with `bwrap: No permissions to create new namespace`, with no fallback (verified live in #53). So the app probes before each session (both helpers present, and `bwrap --unshare-user --ro-bind / / true` succeeds; on failure `kernel.apparmor_restrict_unprivileged_userns` names the reason for the notice) and starts the Sandbox off when the probe fails: `sandbox.enabled: false` for Claude, `danger-full-access` for Codex. What Codex's approvals are in that state is [#56](https://github.com/qodesmith/unimatrix-zero/issues/56).
- **YOLO removes approvals and the Sandbox together**: Claude `bypassPermissions` with the Sandbox off, Codex `danger-full-access` with `approval_policy: never`. The YOLO confirmation says so. Tools and tiers are unchanged. Amends #9's YOLO definition by one clause.
- **Write files Workspaces are untouched.** They have no shell, so there is nothing to sandbox; file writes are governed by the tier as before.
- **[ADR 0014](./0014-electron-security-posture.md)'s "the vendor sandboxes' job"** is this decision.
- **Verified live in [#53](https://github.com/qodesmith/unimatrix-zero/issues/53)** on 2026-10-17 (Agent SDK 0.3.302, Codex 0.163.0, macOS and Ubuntu 24.04 in Docker): the fence holds as written on both vendors; the four corrections above (the ask rule beside every allow rule, the `SandboxNetworkAccess` prompt, helpers on `PATH`, probing before the session) are where it differed. Denied reads and writes have different wording on Linux (`No such file or directory`, `Read-only file system`) than on macOS (`Operation not permitted`). One edge is still undecided, in [#56](https://github.com/qodesmith/unimatrix-zero/issues/56): with the Sandbox on, Claude runs sandboxed commands with no card at all (`autoAllowBashIfSandboxed` defaults to true), so "the tiers and cards stand unchanged" holds only with it set to false. Still from docs only: native Windows. The desktop apps' own behaviour is awaited in [#55](https://github.com/qodesmith/unimatrix-zero/issues/55).
