# Commands run inside the vendor Sandbox, set the way the vendor's desktop app sets it; YOLO removes it

The approval card decides whether a command runs; nothing decided what an approved command can reach. Once allowed, a command runs as the user, with `~/.ssh`, `~/.aws`, `~/.config/gh` and the open internet, and a prompt injection in a README or a confused Model can make a harmless-looking command carry any of that out. Both vendor programs ship an operating-system Sandbox for exactly this (Seatbelt on macOS, bubblewrap on Linux), and both vendors' own desktop apps turn it on by default and ask only when a command wants out; fewer prompts and a Sandbox are the same decision. We do the same: every command in a Write files + run commands Workspace runs inside the vendor's Sandbox, configured to what that vendor's desktop app does, and YOLO removes it for people who, like a developer running `claude --dangerously-skip-permissions`, take that risk themselves. Nothing happens unless we do it: [ADR 0008](./0008-app-managed-vendor-programs.md) isolates our vendor copies from any user config, and Claude's Sandbox is off until the app turns it on. T3 Code never turns it on for Claude. Findings: [Vendor sandboxing for commands the AI runs](https://github.com/qodesmith/unimatrix-zero/issues/49), which holds the fact-finding. Live tests and their results: [#53](https://github.com/qodesmith/unimatrix-zero/issues/53); the four edges they corrected are marked below.

## Considered Options

- **Approvals only, no Sandbox** (what T3 Code does for Claude, and both vendors in its default Full access mode). Rejected: the card judges intent from one line the AI wrote, in a few seconds. It cannot judge reach.
- **The Sandbox as a reason to approve less.** Rejected: both Sandboxes cover shell commands only; file tools, web fetch, MCP servers and hooks run outside them, Codex never restricts reads, and Claude has none on native Windows. A user who approves on the strength of the Sandbox accepts exposures they cannot see. The tiers and cards from [#9](https://github.com/qodesmith/unimatrix-zero/issues/9) and [#24](https://github.com/qodesmith/unimatrix-zero/issues/24) stand unchanged wherever a card fires; the Sandbox is the floor under them. Inside the Sandbox no card fires at all (below): that is the desktop apps' behavior and the "fewer prompts" this decision trades on, not a weaker card.
- **Folder-only reads, as Cowork does.** Rejected: Cowork runs Claude in a Linux VM with its own toolchain, so hiding everything outside the attached folder costs nothing. We run on the user's machine with the user's node, bun and brew, so commands must read outside the working copy or nothing builds. Codex cannot restrict reads anyway.
- **Keeping the Sandbox on under YOLO**, as a second switch. Rejected: YOLO is the developer's `cc` alias, and two switches is the nuance this decision exists to remove. #9's rule that YOLO "never widens what a Tree can do" was about tools and tiers and still holds: tools that are off stay off, write-only stays write-only, plain Trees stay plain.
- **Refusing run commands where the Sandbox is unavailable.** Rejected: worse than the desktop apps for every Claude user on Windows, and for Codex users on a Windows older than MXC's minimum. The user chose run commands; they are told once instead.

## Consequences

- **Amended by [ADR 0022](./0022-one-kind-of-tree-and-permission-modes.md): the Sandbox is no longer the default, and YOLO is gone.** Every Tree can now run commands, under a Permission mode set in Settings. Full access, the default, removes approvals and the Sandbox together exactly as YOLO did below (Claude `bypassPermissions`, Codex `danger-full-access` with `approval_policy: never`); every "YOLO" below reads as Full access. Everything below about the Sandbox's configuration holds under Auto, Auto-accept edits and Supervised. "Inside the Sandbox, no card" still holds under Auto-accept edits; under Auto the vendor's Reviewer, not the user, answers a request to leave the Sandbox; under Supervised every command the vendor does not recognize as read-only gets a card. There are no Write files Workspaces, tiers or plain Trees any more, and reads never ask, so a read the deny list covers is refused, not carded. The opening's "we do the same" as the desktop apps' default therefore no longer describes the default.
- **Codex: ChatGPT desktop's defaults, as-is.** `workspace-write` with network off and approvals `on-request`, reviewed by the user. Writable roots are the working copy, the temp folders and the package caches below; reads are the whole disk, because Codex has no deny-read outside experimental profiles. A command that needs more asks up front (`require_escalated`), which arrives as an approval request and becomes the card below. `danger-full-access` with `approval_policy: never` exists only under YOLO.
- **Claude: Cowork's intent through the SDK Sandbox.** `Options.sandbox` with `enabled`, writes allowed only in the working copy, temp and the package caches below, and a credentials deny list (`~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.kube`, `~/.gnupg`, keychains, and the Provider folders in our own `userData`) mirrored as `Read(...)` deny rules so the Read tool is covered too, which the SDK merges into the Sandbox's own list. Network is default-deny with an empty allowlist. `allowUnsandboxedCommands` stays true so the hatch below exists; `failIfUnavailable` is false, and since the SDK reports availability only as a line on stderr, the app probes before the session (below). Because it rides the `--settings` layer it works with `settingSources: []`, and a linked folder's `.claude/settings.json` cannot loosen it.
- **Reads are the whole disk minus credentials, on both.** That is the one place we differ from Cowork, for the reason above, and it matches what the vendor CLIs do.
- **Asking at the Sandbox boundary is one card.** When the Sandbox blocks a command (a path, the network), the Model asks to run it outside: Claude's `dangerouslyDisableSandbox` retry reaches `canUseTool`, Codex's escalation arrives as `requestApproval`. Both become an approval card that says the command would run outside the Sandbox. "Always allow this command in this Tree" given on that card covers only the outside-the-Sandbox form of that command, and a plain always-allow never covers it. That last clause is not an SDK property but something the app builds (verified live in #53): a `Bash(...)` allow rule, from `permissions.allow` or `allowedTools`, approves the retry with no callback, so every Bash allow rule the app writes is accompanied in the same app-owned `settings` block by the ask rule `Bash(dangerouslyDisableSandbox:true)`, which takes precedence and brings the retry back to `canUseTool`. `bypassPermissions` lets the Model leave silently too, and is never in force outside YOLO. Claude has a second trigger at the Sandbox boundary: a blocked connection arrives as `canUseTool` with `toolName: "SandboxNetworkAccess"` and the host, with a suggested per-host `WebFetch(domain:…)` rule; approving it opens that host and keeps the command inside the Sandbox. Both are the same card family: the retry's card says the command would run outside the Sandbox, the network card says which host the command wants. "Always allow" on the network card is the per-host rule the SDK suggests; on the retry it is the outside-the-Sandbox form of that command, as above.
- **Inside the Sandbox, no card.** A command that stays inside the Sandbox runs without asking, on both vendors: Claude's `autoAllowBashIfSandboxed` stays at its default of true, and Codex's sandboxed attempt never asks under `on-request`. Cards remain for everything the Sandbox does not cover (the Sandbox boundary itself, the Read deny rules, file tools, web fetch, MCP servers) exactly as #9 wrote them. This is what Cowork and ChatGPT desktop do, and it is the "fewer prompts" the opening paragraph trades on; amends #9's per-command card by one clause. Verified live in #53.
- **Network is closed by default on both.** ChatGPT desktop closes it; Cowork does not, and that is the one place its defaults are not ours: Cowork's VM holds none of the user's credentials, so an open network leaks nothing, while our Sandbox runs on the user's machine with whole-disk reads, so an open network would let an injected command carry anything readable out (watched live in [#55](https://github.com/qodesmith/unimatrix-zero/issues/55)). A command that needs it goes through the card, and "Always allow" keeps `bun add` from asking twice. No built-in allowlist in v1: if the card fires too often for registries, a short allowlist is a follow-up, not a change of rule; the per-host rule the SDK suggests does not change that, since a user's always-allows are their own allowlist, built by use. **The standard per-user package caches are writable** on both vendors (bun, npm, pnpm, yarn, pip, cargo and the OS cache folder), one fixed list for every Workspace: they hold no credentials, and without them `bun add` fails on `~/.bun` before it reaches the network on both vendors (verified live in #53), so the card would fire for every install and the approved form would run the whole install outside the Sandbox. The per-Workspace Setup command from [ADR 0010](./0010-linked-folder-holds-one-thread.md) is the user's own command, not the AI's, and runs outside the Sandbox. MCP servers and web search run outside the Sandbox on both vendors and keep their own approvals from #9.
- **Other Branches' working copies and the hidden store** are on the deny list on both vendors, so #24's hard deny is enforced by the operating system rather than by a hook, except under YOLO where the hook and the auto-declined approval are all that remain.
- **Subagents** run inside the parent's Sandbox on both vendors; there is no per-Subagent setting.
- **Linux: the app ships bubblewrap and socat** as app-managed helpers downloaded beside the vendor programs, hashed in the manifest, and placed first on Claude's `PATH` through `Options.env`; `bwrapPath` and `socatPath` are honored only from the root-owned managed settings file, which the app cannot write (verified live in #53). The shipped socat is static or carries its libraries, and bwrap is the real binary, not a wrapper. Codex brings its own. Amends ADR 0008. Where unprivileged user namespaces are blocked (Ubuntu 24.04's AppArmor default) the Sandbox is unavailable, below.
- **Windows: Codex runs inside MXC; Claude has no Sandbox.** ChatGPT desktop turns Codex's Windows Sandbox on, so we do too (watched live in [#58](https://github.com/qodesmith/unimatrix-zero/issues/58), which corrected this decision's earlier "off by default, not turned on in v1"). Its choice is MXC, Codex's newer process isolation that needs no administrator setup, no extra Windows accounts and no firewall rules, and which the desktop app prefers for consumer accounts whenever the device allows: Windows 11 24H2 from build 26100.9278 or 25H2 from 26200.9278. The app sets `features.prefer_mxc = true` in its own Codex config folder ([ADR 0008](./0008-app-managed-vendor-programs.md)) with the same `workspace-write`, network off and `on-request` as everywhere else, and inside it Codex behaves as on macOS: commands run as the user, reads are the whole disk (`%USERPROFILE%\.ssh` listed with no card), `curl` fails with `Could not resolve host`, and the retry outside the Sandbox and a write outside the folder each bring a card. The legacy modes are never used: `elevated` needs a UAC prompt, creates two local users (`CodexSandboxOffline`, `CodexSandboxOnline`) and a group, installs firewall filters and sweeps the user's profile granting read ACLs, all of which the desktop app did on first folder open before settling on MXC, and none of which our audience should be asked to approve; `unelevated` has weaker network isolation and no denied reads. Codex only logs MXC availability (`MXC availability: true` in its sandbox log), so the app's Windows probe is the build number, and below the minimum the Sandbox is unavailable, below. Claude's SDK has no Windows Sandbox outside WSL2, and Cowork does not use it either (its Windows shell is a downloaded Ubuntu VM, below), so Claude Trees on Windows take the unavailable path.
- **Where the Sandbox is unavailable, commands still run and the user is told once.** Claude on native Windows (no Windows Sandbox outside WSL2), Codex on a Windows below MXC's minimum build (above), and Linux where bubblewrap cannot run. Choosing a Permission mode that uses the Sandbox there shows a one-time notice that commands run without it, and Settings says so while that mode is on (amended by ADR 0022, which replaced the run-commands tier with Permission modes). Never silently, which is what Codex does on its own when its Windows Sandbox is off. Neither vendor detects "present but cannot run": where user namespaces are blocked, both start normally and then every command fails with `bwrap: No permissions to create new namespace`, with no fallback (verified live in #53). So the app probes before each session (both helpers present, and `bwrap --unshare-user --ro-bind / / true` succeeds; on failure `kernel.apparmor_restrict_unprivileged_userns` names the reason for the notice) and starts the Sandbox off when the probe fails: `sandbox.enabled: false` for Claude, `danger-full-access` with `approval_policy: "untrusted"` for Codex, because `on-request` has nothing to ask about without a Sandbox and losing the floor must not also remove the cards.
- **YOLO removes approvals and the Sandbox together**: Claude `bypassPermissions` with the Sandbox off, Codex `danger-full-access` with `approval_policy: never`. The YOLO confirmation says so. Tools and tiers are unchanged. Amends #9's YOLO definition by one clause.
- **Write files Workspaces are untouched.** They have no shell, so there is nothing to sandbox; file writes are governed by the tier as before.
- **[ADR 0014](./0014-electron-security-posture.md)'s "the vendor sandboxes' job"** is this decision.
- **Verified live in [#53](https://github.com/qodesmith/unimatrix-zero/issues/53)** on 2026-10-17 (Agent SDK 0.3.302, Codex 0.163.0, macOS and Ubuntu 24.04 in Docker): the Sandbox holds as written on both vendors; the four corrections above (the ask rule beside every allow rule, the `SandboxNetworkAccess` prompt, helpers on `PATH`, probing before the session) are where it differed. Denied reads and writes have different wording on Linux (`No such file or directory`, `Read-only file system`) than on macOS (`Operation not permitted`). The four edges the tests exposed as open (no card inside the Sandbox, the package caches, Codex's approvals without a Sandbox, the two network cards) are decided above, from this decision's own principle of doing what the desktop apps do; [#56](https://github.com/qodesmith/unimatrix-zero/issues/56) records them. **The desktop apps were watched in [#55](https://github.com/qodesmith/unimatrix-zero/issues/55)** on macOS the same day: Cowork's shell is a Linux VM that cannot see the Mac's `~/.ssh`, asks to connect the Desktop before writing there, and reaches the internet without asking; Codex runs on the Mac as the user, lists `~/.ssh`, cannot resolve hosts inside the Sandbox, and asks before writing outside the folder. Everything matched this decision except Cowork's open network, kept closed on purpose above. **Native Windows was watched in [#58](https://github.com/qodesmith/unimatrix-zero/issues/58)** on 2026-10-17 (Windows 11 25H2 build 26200.9711; Claude Desktop; the OpenAI.Codex Store app 26.1013 running codex-cli 0.163.0-alpha.10.2): Cowork downloads an Ubuntu 22.04 VM onto the PC on first use (until it arrives only the folder-bridge file tools work, no shell), then runs as `claude` under `/sessions/`, cannot see `C:\Users\…\.ssh`, reaches the internet without asking, and asks to connect the Desktop before writing there, the same as on macOS. ChatGPT desktop ran the administrator-approved `elevated` setup on first folder open and then every command under MXC: `whoami` is the user, `.ssh` is readable with no card, `curl` fails with `Could not resolve host`, the retry outside the Sandbox asked, and the Desktop write asked. One line was wrong, that Codex's Windows Sandbox is off and not turned on in v1; corrected in the Windows consequence above.
- **Amended: the "Sandbox unavailable" notice and the cards at the Sandbox boundary say, in plain words, what changes for the user.** The notice names no AppArmor, user namespaces, bubblewrap or Windows build: the probe's reason only picks which notice shows. It says that on this computer the AI's commands aren't kept to the Tree's files and off the internet, and what the mode still does: its cards, or under Auto its Reviewer. Where a Windows update would bring the Sandbox (Codex below MXC's minimum build), it says to update Windows. The retry's card and Claude's network card each lead with what the command could then read, change or reach, not only that it runs outside the Sandbox or which host it wants. Findings: [#285](https://github.com/qodesmith/unimatrix-zero/issues/285).
- **Amended: under Supervised, Codex runs under a permission profile, so an allowed command cannot leave the Sandbox.** `workspace-write` with approvals `untrusted` did not do what this decision and ADR 0022 said it did. Once the user allows a command and the Sandbox blocks it, Codex runs it again outside the Sandbox and does not ask a second time: one "Allow once", and a write to the home folder went through. `untrusted` reruns, and so does `granular` with `sandbox_approval: true`; `on-request` never does, so Auto and Auto-accept edits stay as written above. Codex refuses the rerun when the policy in force denies any read, since leaving the Sandbox would grant that read. So a Supervised thread names a profile of the app's own in its `config`, which extends Codex's built-in `:workspace` and takes the place of `workspace-write`; sending the `sandbox` setting when the thread starts would drop the profile and bring the rerun back. The profile denies reads of the credentials list above, the app's own hidden folders and other Trees' files, allows writes in the Tree's folder, temp and the package caches, and keeps the network off. This corrects "Codex has no deny-read outside experimental profiles" and "Codex never restricts reads": a profile needs no experimental API, the Sandbox itself refuses a command's read of a denied folder (`Operation not permitted`), and leaving the Sandbox does not lift the denial.
  - **Leaving the Sandbox.** An allowed command that the Sandbox blocks now fails, with no rerun and no second card. A blocked connection fails, as it did before. The Model can still ask up front to run a command outside (`require_escalated`); that request brings the card that says the command would run outside the Sandbox, and its "Always allow" covers only that form.
  - **Edits are not commands.** The Sandbox holds commands only, as it always did. An edit outside the Tree's folder still gets its own card, which names the file, and is written once allowed.
  - **One limit stands.** The only mark on that request is the Model's reason for it, and Codex does not make the Model give one. An escalation without a reason would show the plain command card and then run outside the Sandbox, still unable to read the denied folders. In three live runs the Model always gave one.
  - **Rejected.** Keeping `untrusted` as it was and wording every Codex command card as "may run outside the Sandbox": the Sandbox would limit nothing for an approved command. `granular` with `sandbox_approval: true`, and a `PreToolUse` hook of the app's own that holds each command for a card: the whole spec, but it needs a hook program, a channel back to the host and the experimental API. `on-request` under Supervised: its card at the Sandbox boundary is true, but no command inside gets a card, which is Auto-accept edits. Waiting for OpenAI: the rule is unchanged at Codex 0.172.0.
  - Where the Sandbox is unavailable nothing changes: `danger-full-access` with `approval_policy: "untrusted"`. Verified live on Codex 0.163.0 on macOS on 2026-11-26, and read in Codex's source at `rust-v0.163.0`. Findings: [#92](https://github.com/qodesmith/unimatrix-zero/issues/92).
- **Amended: on Claude, a hook keeps Read, Glob and Grep out of other Trees' files.** Claude's Sandbox holds commands only, so it hides other Trees from commands and not from the file tools. A `Read(...)` deny rule can't hide them either: it would name the folder that holds every Tree's files, and so hide the Tree's own. So under Supervised a hook refuses a Read, Glob or Grep of another Tree's files, and a Glob or Grep that starts at or above the folder of every Tree, since that search would walk into them. A search of the home folder is refused for that reason, and the Model is told to search a narrower folder. This corrects two lines above for those three tools on Claude: "reads are the whole disk minus credentials", and other Trees' files "enforced by the operating system rather than by a hook". The operating system still refuses a command that reads them. Findings: [#92](https://github.com/qodesmith/unimatrix-zero/issues/92).
