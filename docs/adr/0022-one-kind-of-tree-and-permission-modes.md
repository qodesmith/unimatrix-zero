# One kind of Tree under a Permission mode, Full access by default; attachments reach the AI by path

[#9](https://github.com/qodesmith/unimatrix-zero/issues/9) made Trees plain by default (no files: Claude with `tools: []`, Codex locked down in layers) and made a Workspace an opt-in property with two tiers, write files or write files and run commands, either app-owned or in a linked folder. [ADR 0018](./0018-commands-run-inside-the-vendor-sandbox.md) put every command inside the vendor Sandbox, with YOLO, a global Setting off by default, as the one way out. [PRD §6](../prd/01-initial-release/06-the-input-prompts-attachments-models.md) took only images, PDFs and UTF-8 text, all inline, and rendered PDFs page by page for ChatGPT. #9's own constraints were to never artificially limit power users, to stay effortless for non-technical users, and to keep branching coherent. Only the last argued for limits, and it is about writes, not reads. Meanwhile a user expects to attach any file, or ask the AI to read `~/repos/x`, in any Tree. So there is one kind of Tree: every Tree can read files anywhere on disk, write files and run commands, as far as its **Permission mode** allows, and the user never sees the word Workspace. There are four Permission modes, modeled on T3 Code's, set in Settings, and the default is **Full access**. An attachment of any type is kept as a copy and reaches the AI by its path, and also inline where the Model takes that type natively and cheaply. Text and page images are extracted from it when it is attached, in a hidden, sandboxed Chromium window. Decided after comparing the old model with T3 Code (commit `d3c91008`).

## Considered Options

- **Keeping plain Trees, with a read-only tool scoped to the Tree's attachments.** Rejected: it fixes attachments and nothing else. "Read `~/repos/x`" would still need a Workspace, the user would still have to learn the plain and Workspace split, and since Codex has no tool that reads only some paths, the tool would be our own MCP server beside a locked-down Codex.
- **Reads behind a per-folder approval card.** Rejected: Codex cannot restrict reads in any sandbox mode, so the card would be a promise only Claude keeps.
- **Inline-only attachments**, as before. Rejected: each Provider takes few types inline (Codex only images). Claude caps the images and documents in one request and drops the oldest without a word, and `/compact` strips media from the session. Every other type would need a conversion in the app, a heavy one, on every hand-over.
- **No extraction, only the path.** Rejected after a live run (Codex 0.169, Full access, a PDF's path in the Prompt). With Homebrew's poppler installed, Codex used `pdftotext`: 8 s and 31k input tokens. Without Homebrew it fell back to Python workarounds or to `pip install pypdf` from the internet: 23 to 29 s and about 95k tokens, and the network route fails in every mode where the Sandbox closes the network. On a Mac with neither Homebrew nor the developer tools, only `sips` is left, which renders the first page only. T3 Code extracts office formats to a `.txt` next to the original at upload, never PDFs, and gives the Model only paths.
- **pdf.js and `@napi-rs/canvas` in a Node process**, as [PR #256](https://github.com/qodesmith/unimatrix-zero/pull/256) does in the Provider host. Rejected: native code outside the shell, against [ADR 0007](./0007-thin-shell-signed-app-bundles.md), and a parser with Node's privileges running on files that [ADR 0014](./0014-electron-security-posture.md) treats as hostile.
- **Full access off by default**, as YOLO was, starting in Supervised or Auto-accept edits. Rejected: T3 Code starts at full access, and developers expect a tool like this to behave like `claude --dangerously-skip-permissions`. The maintainer accepts the risk below for every user.

## Consequences

- **Four Permission modes, one global Setting, Full access by default.** It replaces YOLO. Tools switched off in the Tools panel stay off in every mode, and "Always allow in this Tree" still covers trust in one Tree.
  - **Full access:** no approval cards and no Sandbox. Claude `permissionMode: 'bypassPermissions'` with `allowDangerouslySkipPermissions`; Codex `danger-full-access` with `approval_policy: never`.
  - **Auto:** the vendor's own reviewer decides. Claude `permissionMode: 'auto'` (present in Agent SDK 0.3.307); Codex `on-request` with its `auto_review` reviewer.
  - **Auto-accept edits:** edits inside the Tree's files go ahead; edits elsewhere and commands get an approval card. Commands run inside the vendor Sandbox.
  - **Supervised:** every edit and every command gets an approval card. Commands run inside the vendor Sandbox.
- **Reads never ask, in any mode.** Codex cannot restrict reads, so a read card would be a promise only Claude keeps.
- **Full access protects nothing, credentials included.** Codex cannot restrict reads, and Read deny rules do not stop a Claude Bash `cat ~/.ssh/...`. The maintainer accepts this. Under Full access the operating system no longer enforces #24's hard deny on other Branches' working copies and the hidden store; only what ADR 0018 left under YOLO remains.
- **ADR 0018's Sandbox holds under Auto-accept edits and Supervised**, with its configuration unchanged: writes only in the working copy, temp and the package caches, the credentials deny list, the closed network, the platform helpers and probes, and the path for where it is unavailable. A read the deny list covers is refused there, never asked. In both modes every command gets a card, so ADR 0018's "inside the Sandbox, no card" no longer holds; the Sandbox decides only what an approved command can reach.
- **Every Tree has files.** Without a linked folder they live in the Tree's own folder in `userData`, which the app shows only from the AI's first write. Snapshots, working copies and the hidden store ([ADR 0010](./0010-linked-folder-holds-one-thread.md), PRD §9) are unchanged, one store per Tree. "Work in a folder…" makes a folder of the user's the Tree's linked folder: the AI works there, the folder's `CLAUDE.md` and `AGENTS.md` load, and one Thread at a time is in the folder, which the UI names. Which Thread is in the folder is the one part of the old Workspace the user still deals with.
- **Writes outside the Tree's files are not versioned.** Where the mode allows them (`~/.zshrc`, say), they change the one real file every Branch shares, and no Snapshot holds them. The Reply marks each such edit _not versioned_.
- **An attachment is a copy, given to the AI by path.** Any type is accepted. The app keeps the copy in `userData/attachments/` ([ADR 0001](./0001-app-owns-the-tree.md): the Tree owns its originals), and the Prompt carries one line per attachment with its path, as T3 Code does (`[Attached file "x" is saved at: …]`), so the AI opens it with its own tools. Attaching freezes the file as it was at send time; naming a path in a Prompt reads the live file.
- **Inline as well, where the Model takes the type natively and it is cheap:** images on both Providers (Codex as `data:` URLs), PDFs on Claude within a media budget for the whole request, and small UTF-8 text files. Past the budget a PDF goes by path only, since Claude's per-request caps would otherwise drop older media without a word.
- **The attachment chip says what the Model can do with the file**, such as "ChatGPT will open this with its tools" or "Neither Model can play audio". A folder dropped on the Input becomes a chip holding its path, copies nothing, and offers "Work in this folder".
- **Extraction at attach time, in a hidden, sandboxed Chromium window.** Office files (docx, xlsx, pptx, odt, ods, odp, rtf, epub, ipynb) become text. A PDF becomes text per page, plus a PNG (1600 px on its long side) of each page that has no text or has images over 10% of it. The window has no Node, no file system and no network: main passes the bytes in and validates what comes back, each job has a timeout and caps on size and zip expansion, and a failed job leaves the attachment with its path only. The extracted files are stored next to the original and deleted with it, and the AI gets their paths beside the original's. No native code is involved, so ADR 0007 no longer has an exception to make, and a hostile file is parsed where it can reach nothing. **This rests on a spike, running when this was written, that verifies the hidden window; if the spike fails, this consequence is reopened.**
- **What this supersedes and amends.**
  - #9: plain Trees and the Codex lockdown layers, the write files and run commands tiers, YOLO, and the attachment rule (already amended once by PRD §6).
  - [#24](https://github.com/qodesmith/unimatrix-zero/issues/24): the two choices per Workspace, and app-owned files as an option rather than every Tree's starting point.
  - PRD §6's attachment rule and PR #256's PDF conversion in the Provider host.
  - ADR 0018: its "Sandbox by default" and YOLO clauses, and "inside the Sandbox, no card".
  - ADR 0007, ADR 0010, ADR 0011, ADR 0014 and ADR 0017, each by an amendment note.
- **Workspace, plain Tree and YOLO leave the vocabulary.** In older tickets and ADRs, a Workspace reads as the Tree's files, and YOLO as Full access.
- **Provider dependency entries that assume a Claude with no tools** (`verbatim-prompts`, `setup-tokens`) and a Codex that sends no server requests (`codex-server-requests-refused`) go stale when this is built, and change with that code.

## Open questions

- **Which system prompt every Tree runs.** #9 gave Trees with run commands the vendors' agent prompts (Claude's `claude_code` preset, Codex's base instructions) with the user's System prompt appended, and gave every other Tree the System prompt alone. Now every Tree can run commands. Whether every Tree takes the agent prompts, and what that does to the cold first Turn on Claude, which re-reads about 36k tokens of Claude Code's prompt and tool definitions ([#7](https://github.com/qodesmith/unimatrix-zero/issues/7), #9) on the $20 plans, is not decided.
- **Auto:** whether commands stay inside the Sandbox, and what the user sees when the vendor's reviewer refuses something.
- **Codex's settings for Auto-accept edits and Supervised** that produce exactly the cards above, and Claude's (`acceptEdits` and `default`, with the Sandbox's automatic approval of sandboxed commands turned off).
- **Whether the Permission mode is only global**, or also chosen per Tree or per Prompt as in T3 Code, and when a change reaches a Reply that is streaming.
- **How a command's write outside the Tree's files gets its not-versioned mark.** A file tool names the path it edits; a shell command does not.
- **"Work in a folder…" on a Tree that already has files of its own.** [#27](https://github.com/qodesmith/unimatrix-zero/issues/27) allowed moving app-owned files only into a new or empty folder; whether a Tree can also leave its folder is open too.
- **The size of Claude's media budget**, and which media go by path only once it is reached.
