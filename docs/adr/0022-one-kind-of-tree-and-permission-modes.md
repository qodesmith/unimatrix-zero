# One kind of Tree under a Permission mode, Full access by default; attachments reach the AI by path

[#9](https://github.com/qodesmith/unimatrix-zero/issues/9) made Trees plain by default (no files: Claude with `tools: []`, Codex locked down in layers) and made a Workspace an opt-in property with two tiers, write files or write files and run commands, either app-owned or in a linked folder. [ADR 0018](./0018-commands-run-inside-the-vendor-sandbox.md) put every command inside the vendor Sandbox, with YOLO, a global Setting off by default, as the one way out. [PRD §6](../prd/01-initial-release/06-the-input-prompts-attachments-models.md) took only images, PDFs and UTF-8 text, all inline, and rendered PDFs page by page for ChatGPT. #9's own constraints were to never artificially limit power users, to stay effortless for non-technical users, and to keep branching coherent. Only the last argued for limits, and it is about writes, not reads. Meanwhile a user expects to attach any file, or ask the AI to read `~/repos/x`, in any Tree. So there is one kind of Tree: every Tree can read files anywhere on disk, write files and run commands, as far as its **Permission mode** allows, and the user never sees the word Workspace. There are four Permission modes, modeled on T3 Code's, set in Settings or beside the Input, and the default is **Full access**. An attachment of any type is kept as a copy and reaches the AI by its path, and also inline where the Model takes that type natively and cheaply. Text and page images are extracted from it when it is attached, in a hidden, sandboxed Chromium window. Decided after comparing the old model with T3 Code (commit `d3c91008`).

## Considered Options

- **Keeping plain Trees, with a read-only tool scoped to the Tree's attachments.** Rejected: it fixes attachments and nothing else. "Read `~/repos/x`" would still need a Workspace, the user would still have to learn the plain and Workspace split, and since Codex has no tool that reads only some paths, the tool would be our own MCP server beside a locked-down Codex.
- **Reads behind a per-folder approval card.** Rejected: Codex cannot restrict reads in any sandbox mode, so the card would be a promise only Claude keeps.
- **Inline-only attachments**, as before. Rejected: each Provider takes few types inline (Codex only images). Claude caps the images and documents in one request and drops the oldest without a word, and `/compact` strips media from the session. Every other type would need a conversion in the app, a heavy one, on every hand-over.
- **No extraction, only the path.** Rejected after a live run (Codex 0.169, Full access, a PDF's path in the Prompt). With Homebrew's poppler installed, Codex used `pdftotext`: 8 s and 31k input tokens. Without Homebrew it fell back to Python workarounds or to `pip install pypdf` from the internet: 23 to 29 s and about 95k tokens, and the network route fails in every mode where the Sandbox closes the network. On a Mac with neither Homebrew nor the developer tools, only `sips` is left, which renders the first page only. T3 Code extracts office formats to a `.txt` next to the original at upload, never PDFs, and gives the Model only paths.
- **pdf.js and `@napi-rs/canvas` in a Node process**, as [PR #256](https://github.com/qodesmith/unimatrix-zero/pull/256) does in the Provider host. Rejected: native code outside the shell, against [ADR 0007](./0007-thin-shell-signed-app-bundles.md), and a parser with Node's privileges running on files that [ADR 0014](./0014-electron-security-posture.md) treats as hostile.
- **Full access off by default**, as YOLO was, starting in Supervised or Auto-accept edits. Rejected: T3 Code starts at full access, and developers expect a tool like this to behave like `claude --dangerously-skip-permissions`. The maintainer accepts the risk below for every user.

## Consequences

- **Four Permission modes, one global Setting, Full access by default.** It replaces YOLO. Tools switched off in the Tools panel stay off in every mode, and "Always allow in this Tree" still covers trust in one Tree.
  - **Full access:** no approval cards and no Sandbox. Claude `permissionMode: 'bypassPermissions'` with `allowDangerouslySkipPermissions`; Codex `danger-full-access` with `approval_policy: never`.
  - **Auto:** the vendor's own Reviewer decides, inside the Sandbox. Claude `permissionMode: 'auto'` (present in Agent SDK 0.3.307) with the Sandbox on: a model classifier approves or denies each call, and asks through `canUseTool` when it cannot decide. Codex `workspace-write` with approvals `on-request` and `approvalsReviewer: 'auto_review'`: a prompted subagent weighs the risk of each approval request (leaving the Sandbox, the network, MCP approvals, permission requests) in the user's place. Each review is one more model call, which uses the plan's limits and takes time.
  - **Auto-accept edits:** edits inside the Tree's files go ahead, and edits elsewhere get an approval card. Commands run inside the vendor Sandbox without asking; a command that needs to leave it (a blocked path or the network) gets a card, as ADR 0018 decided. Claude `acceptEdits` with sandboxed commands approved automatically; Codex `workspace-write` with approvals `on-request`.
  - **Supervised:** every edit gets an approval card, and so does every command the vendor does not recognize as read-only. Commands it does recognize (`ls`, `cat`, `grep` and the like) run without a card, since reads never ask. Commands run inside the vendor Sandbox. Codex `workspace-write` with approvals `untrusted`, which runs its known-safe read-only commands and asks for the rest, as T3 Code's Supervised does. Claude `default` with the Sandbox's automatic approval of sandboxed commands off, which leaves read-only commands to Claude's own handling.
- **The Permission mode is global only.** No Tree or Prompt picks its own, as T3 Code allows. A per-Tree override may come later, through whatever [#230](https://github.com/qodesmith/unimatrix-zero/issues/230) decides for Settings in general. A change applies from the next Reply: a Reply already streaming keeps the mode it started with, since Codex fixes a Turn's approval settings when the Turn starts, and Stop is the brake.
- **The mode shows beside the Input** as a small label, as the Model picker does. Clicking it opens a menu that changes the global mode and says "Applies to every Tree from the next Reply". Settings has the same control. The label replaces YOLO's badge.
- **Under Auto, the Reviewer's decision shows in the Reply, and the user cannot overrule it there.** While the Reviewer works, a "Reviewing…" line sits where the action happens. An approval becomes a collapsed "✓ approved by reviewer" chip, which expands to the action and the Reviewer's reason. A refusal becomes a collapsed "✕ declined by reviewer" chip with the reason, and the AI carries on and adapts. There is no "Allow anyway": to push past a refusal, the user says so in the next Prompt or switches mode. A review that times out or fails counts as declined, with the reason "Reviewer didn't answer". When Claude's classifier cannot decide, the usual approval card appears, and its answer collapses into a chip as any card's does.
- **Reads never ask, in any mode.** Codex cannot restrict reads, so a read card would be a promise only Claude keeps.
- **Full access protects nothing, credentials included.** Codex cannot restrict reads, and Read deny rules do not stop a Claude Bash `cat ~/.ssh/...`. The maintainer accepts this. Under Full access the operating system no longer enforces #24's hard deny on other Branches' working copies and the hidden store; only what ADR 0018 left under YOLO remains.
- **ADR 0018's Sandbox holds in every mode but Full access**, with its configuration unchanged: writes only in the working copy, temp and the package caches, the credentials deny list, the closed network, the platform helpers and probes, and the path for where it is unavailable. A read the deny list covers is refused there, never asked. Under Auto the Reviewer decides whether a command may leave the Sandbox, and the Sandbox limits what an approved one reaches. Under Auto-accept edits, ADR 0018's "inside the Sandbox, no card" holds unchanged: a command runs without asking while it stays inside, and leaving the Sandbox gets a card. Under Supervised every command that is not read-only gets a card, and the Sandbox decides what an approved one can reach.
- **Every Tree has files.** Without a linked folder they live in the Tree's own folder in `userData`. Both vendor programs need a working folder that exists when a session starts, so the app makes it, empty, with the Tree's first session, and shows it only from the AI's first write. Snapshots, working copies and the hidden store ([ADR 0010](./0010-linked-folder-holds-one-thread.md), PRD §9) are unchanged, one store per Tree. "Work in a folder…" makes a folder of the user's the Tree's linked folder: the AI works there, the folder's `CLAUDE.md` and `AGENTS.md` load, and one Thread at a time is in the folder, which the UI names. Which Thread is in the folder is the one part of the old Workspace the user still deals with.
- **"Work in a folder…" depends on what the Tree and the folder already hold.** A Tree with no files yet takes the folder as its linked folder. A Tree with files of its own moves them into a new or empty folder, one way, as [#27](https://github.com/qodesmith/unimatrix-zero/issues/27) decided. A Tree with files and a folder that is not empty is refused, with the reason and the way out: pick an empty folder. Merging the two is left out of v1.
- **A Tree can stop working in its linked folder**, through "Stop working in this folder" beside the folder's name in the Files header, not by asking the AI. The real folder is left exactly as it is. The Tree continues from its own folder in `userData`, each Thread's files rebuilt from its latest Snapshot in the hidden store. Ignored files, such as `node_modules`, are not in the store, so the files section of the prompt tells the AI they are missing. The Tree can then pick a folder again under the rules above.
- **Writes outside the Tree's files are not versioned.** Where the mode allows them (`~/.zshrc`, say), they change the one real file every Branch shares, and no Snapshot holds them. The Reply marks _not versioned_ each such edit made by a file tool, which names the path it edits. A shell command's writes outside the Tree's files are not marked; the Reply shows the command itself. This limit is accepted: watching the home folder cannot tell the AI's writes from other apps', and marking every command would be noise.
- **An attachment is a copy, given to the AI by path.** Any type is accepted, with T3 Code's limits: up to 100 attachments per Prompt and 50 MiB per file; an image sent inline is shrunk to at most 2000 px on its long side and 10 MiB, with at most 80 MiB of images per Prompt, while the original is kept as attached. The app keeps the copy in `userData/attachments/` ([ADR 0001](./0001-app-owns-the-tree.md): the Tree owns its originals), and the Prompt carries one line per attachment with its path, as T3 Code does (`[Attached file "x" is saved at: …]`), so the AI opens it with its own tools. Attaching freezes the file as it was at send time; naming a path in a Prompt reads the live file.
- **Inline as well, where the Model takes the type natively and it is cheap:** images on both Providers (Codex as `data:` URLs), PDFs on Claude, and UTF-8 text files up to 32 KB as text. A larger text file goes by path only.
- **Claude's media budget is 20 MiB of base64 and 90 images and documents per request**, counted over the whole Thread being sent. That is below `claude`'s own limits, about 24 MiB and 100, past which it drops the oldest without a word. Past the budget, the oldest attachments go by path only; their path lines stay, so the AI can still open them. The Context size details drawer of a Claude Reply shows the budget in use ("Inline media: 14.2 / 20 MiB · 23 / 90 files") and how many earlier attachments now go by path only, and an earlier Prompt's attachment chip says "Sent by path only now" once its file has left the inline set. The budget is Claude's alone, since `claude`'s limits are why it exists.
- **The attachment chip says what the Model can do with the file**, such as "ChatGPT will open this with its tools" or "Neither Model can play audio". A folder dropped on the Input becomes a chip holding its path, copies nothing, and offers "Work in this folder".
- **Extraction at attach time, in a hidden, sandboxed Chromium window.** Office files (docx, xlsx, pptx, odt, ods, odp, rtf, epub, ipynb) become text. A PDF becomes text per page, plus a JPEG of each page that has no text or has images over 10% of it, for at most 100 pages; past that the PDF gets text only, and its chip says so. Each page image is 1600 px on its long side at about 85% quality, encoded by Chromium's canvas in the window, with no ffmpeg or other outside tool. JPEG rather than PNG because an image's tokens follow its pixel size (on Claude about width × height / 750), not its bytes: the format saves disk and request bytes, which count against Claude's media budget, while the 1600 px cap sets the tokens. The window has no Node, no file system and no network: main passes the bytes in and validates what comes back, each image a JPEG within the expected dimensions. A job takes input up to 50 MiB (the attachment limit), with 60 s per file and a cap on zip expansion. Each job gets a window of its own, because the spike found the renderer keeps its peak memory after a job. A failed job leaves the attachment with its path only. The extracted files are stored next to the original and deleted with it, and the AI gets their paths beside the original's. No native code is involved, so ADR 0007 no longer has an exception to make, and a hostile file is parsed where it can reach nothing. A spike on Electron 45 verified the hidden window ([#262](https://github.com/qodesmith/unimatrix-zero/issues/262#issuecomment-6950240100)): no Node and no network inside it, a 300-page PDF in about 2 s, a fresh window about 120 ms after a hang or a crash, and zip bombs and XML entity attacks refused. Windows, Linux, a packaged build and real hostile PDFs were not tested.
- **Every Tree runs the vendors' own agent prompts, with the System prompt added after them**, as T3 Code does (commit `d3c91008`: Claude `systemPrompt: {type: 'preset', preset: 'claude_code', append}`; Codex keeps its base instructions). They carry the vendors' tuning for using the tools well, which a replacement would throw away. The cost is a larger cold first Turn on Claude, about 36k tokens of Claude Code's prompt and tool definitions in [#7](https://github.com/qodesmith/unimatrix-zero/issues/7), mostly cached after it; it is measured again while building this. The System prompt no longer replaces the vendors' prompts in any Tree.
- **ChatGPT Trees load Skills the way Codex does on its own.** Codex can read a Skill's files in every Tree now, so the app-owned `read_skill` MCP tool and the "needs a Workspace with commands" marking from [#83](https://github.com/qodesmith/unimatrix-zero/issues/83) are dropped.
- **What this supersedes and amends.**
  - #9: plain Trees and the Codex lockdown layers, the write files and run commands tiers, YOLO, the System prompt alone in Trees without commands, and the attachment rule (already amended once by PRD §6).
  - [#24](https://github.com/qodesmith/unimatrix-zero/issues/24): the two choices per Workspace, and app-owned files as an option rather than every Tree's starting point.
  - #83: the `read_skill` MCP tool and the "needs a Workspace with commands" marking.
  - PRD §6's attachment rule and PR #256's PDF conversion in the Provider host.
  - ADR 0018: its "Sandbox by default" and YOLO clauses, and "inside the Sandbox, no card" under Supervised.
  - ADR 0007, ADR 0010, ADR 0011, ADR 0014 and ADR 0017, each by an amendment note.
- **Workspace, plain Tree and YOLO leave the vocabulary.** In older tickets and ADRs, a Workspace reads as the Tree's files, and YOLO as Full access.
- **Provider dependency entries that assume a Claude with no tools** (`verbatim-prompts`, `setup-tokens`) and a Codex that sends no server requests (`codex-server-requests-refused`) go stale when this is built, and change with that code.
