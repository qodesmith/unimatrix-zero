# Reports go through a stateless relay into GitHub Issues

A user who hits a problem sends a **Report**: "Report a problem…" shows the exact issue it will become, and on Send, main posts it to one Cloudflare Worker, which checks it against the same schema the app built it from and files it as an issue through a GitHub App installed on this repo with `issues:write` only, labelled `needs-triage`, and returns the issue number. Nothing is ever sent without that preview and click; there is no "Always send". We chose a relay over a pre-filled GitHub issue as the main channel because the audience includes children and casual users, and "make a GitHub account" is where most reports die. The pre-filled issue stays as the fallback and the diagnostics export as the baseline. This needed the infrastructure rule amended ([ADR 0006](./0006-unsigned-distribution.md)): the Worker is free, keeps nothing, and the app works fully without it. Findings: [Crash and bug reporting without PII](https://github.com/qodesmith/unimatrix-zero/issues/47).

## Considered Options

- **Diagnostics export only.** Ships regardless ([ADR 0014](./0014-electron-security-posture.md)); on its own, almost no report would arrive.
- **A pre-filled GitHub issue as the only channel.** No infrastructure, but needs a GitHub account. Kept as the fallback.
- **A hosted error service** (Sentry, GlitchTip, PostHog). Rejected: a key in the app that anyone can extract, a third party that sees IPs, automatic sending that would need consent screens for a vendor we don't control, and COPPA treats a persistent identifier from a child under 13 as personal information.

## Consequences

- **Every field has a type, never free content.** A field is a version string, a value from an enum we define, an integer, or a stack frame (bundle-relative module path and function name). `error.stack` is parsed into frames and its message line dropped; messages are never sent, and the only message-like field is our own error code from a fixed list. `Error.cause` chains and `AggregateError` members are reduced to class names. A vendor error appears only as its structured code, and only if it is in the list generated from the vendor's own types; anything else is `other`. Nothing is scrubbed after the fact because nothing free-form ever enters, so a prompt injection can't arrange a crash that carries a secret.
- **The fields:** a random id per Report, made at send time and never reused; app, shell and bundle versions; OS and architecture; Electron version; Provider kind and vendor program version; the process that failed (renderer, main or a Provider host) and its exit reason; error class; our error code; our stack frames; the fingerprint; the shape of the Tree (depth, Turn count, Fork count, canvas orientation, whether chat mode was open, Workspace kind and permission, how many Skills, MCP servers and Plugins are on, Theme as a preset name or "custom", and mode); what the user was doing, as both a user-facing group and the last command name from the IPC contract ([ADR 0015](./0015-types-derive-from-schemas-ipc-contract.md)), with "idle or background" when there was no recent command; and the optional description. Never a Tree title, Collection name, Skill or MCP server name, file name or path, Setting value, or conversation content.
- **One schema, two renderings.** The issue body and the diagnostics export are both rendered from the same schema object, and the Worker validates with that schema too, so the Worker lives in the monorepo beside the contract. The issue shows the object once as a fenced JSON block, which the Worker renders from the validated object rather than the client's bytes, and once as readable headings.
- **The description is the one exception**, because Reports without one are rarely useful. It is user-written, so a prompt injection can't reach it, but a child could type a name. It is optional except when there is no error, capped at 2,000 characters, stripped of control characters, and placed in a fenced `text` block whose fence is one longer than the longest run of backticks in it, so mentions, issue links and Markdown stay inert. A triage agent treats it as untrusted data, never as instructions.
- **Main sends, never the renderer.** The renderer sends one command over the bridge with the picker value and the description; main assembles the Report, previews it and posts it. The renderer's CSP still has no http sources, and the request only happens on a click, so ADR 0014's "nothing makes a network request without a click" holds.
- **Builds are unminified, with modules kept as separate files**, loaded from the asar through `app://`, so a frame's path is a real module path and "our top frame" is the first frame under `src`, not `node_modules`. Source maps are not shipped; the release script keeps them per bundle version on the maintainer's machine for reading frames from a bundle no longer checked out.
- **The fingerprint stays the same across releases.** Our error code when there is one; otherwise error class plus the top frame's module and function, without line or column. With no frame of ours, `<Provider kind> <vendor code>` or `<process> exited: <reason>`. Issue titles are `<group>: <ErrorClass or code> in <module>#<function> [fp-<8 hex>]` (no colon in the token, which GitHub search would read as a qualifier), and the Worker searches `"fp-…" in:title`; a failed search files a new issue. The group in the title is the first reporter's.
- **One bug stays one issue.** A match on an open issue updates one Occurrences comment the Worker finds by a marker line (counts per version × OS) and adds a comment only when the Report has a description. The tally is best-effort under GitHub's secondary limits on content creation; if it fails, the Report still counts as filed. A match on an issue closed as fixed in version F (from the manifest's `fixed` list, which the Worker fetches and may cache) is tallied there when the Report is older than F, and opens a new issue linking it when the Report is F or newer: a regression. Issues closed as not planned or as duplicates are tallied. Reports with no error can't be deduplicated; they are labelled `no-error` and only the rate limits bound them. Feature requests typed into the description arrive the same way and are relabelled by hand.
- **The relay keeps nothing.** Workers Logs, Logpush and every observability setting are off in the Worker's configuration, because the defaults can capture request metadata including the client address. The client IP is used only as the rate-limit key for the length of the request; GitHub sees only the Worker. The app already sends the user's IP to GitHub Pages on every update check, so the relay adds no exposure the project hadn't accepted, and with no install id nothing becomes a persistent identifier.
- **Where a Report goes:** the Diagnostics on this machine, trimmed or cleared; the Worker, which keeps nothing; and the GitHub issue, the only lasting copy, holding only what the user previewed. Settings → Updates & About says: "Reports go to a GitHub issue. The app keeps no copy beyond Diagnostics, and the relay keeps nothing."
- **The manifest controls the relay** ([ADR 0007](./0007-thin-shell-signed-app-bundles.md)). Its `reports` field holds the relay URL and whether issues can be opened; with the field absent, every Report uses the fallback, which is the kill switch. The Worker's own configuration (repo, App id and key) stays in the Worker, so moving the relay or pointing it at an intake repo is a Worker change plus a manifest entry, never a bundle release.
- **The fallback.** If the Worker can't be reached or refuses (429), the dialog copies the Report and opens a pre-filled GitHub issue. Offline it says "Couldn't send. Copy the report to send it later." and only Copy works; there is no queue. "Sent as #123" is a link only when the manifest says issues can be opened, so a private repo never shows a child a 404.
- **Rate limits.** The app sends at most once per fingerprint per version, checked against its record of sent Reports, and shows "You've reported this before (#123)" instead. The Worker adds a per-IP limit at the edge, its period set by what the Workers rate-limiting binding supports (per location, 10 or 60 seconds; to verify when writing the Worker). Shared addresses such as schools fall back to the pre-filled issue.
- **The record of sent Reports** (issue number, fingerprint, version, date) is its own small file in `userData`, outside the Diagnostics, because the "already reported" band and the fixed notice need it past 14 days. Clear diagnostics leaves it alone. An entry is dropped once its fixed notice has shown, or at a fixed count. Never archived ([ADR 0011](./0011-archives-are-their-own-versioned-format.md)).
- **Diagnostics hold schema entries only**, never free-text lines, in `userData/logs`, trimmed at 14 days or 5 MB, never archived. Copy diagnostics, Export diagnostics and Clear diagnostics sit in Settings → Updates & About. Entries keep a clock time on disk; what leaves the app shows durations since that session's launch, so an issue never shows when someone uses the app.
- **Crash detection uses our own launch marker and structured records, never Electron's `crashReporter`**, since minidumps carry memory. The launch marker detects a main crash on the next launch; the records are what the band reports. A renderer crash reloads the window and shows the band at once; a Provider host crash's band offers "Download <Provider> again" once restarts are exhausted, and "Report a problem…" if the fresh copy still fails ([ADR 0013](./0013-utility-process-per-provider-main-is-the-hub.md), [#40](https://github.com/qodesmith/unimatrix-zero/issues/40)). Non-fatal errors never prompt. One band at a time; Dismiss forgets the band, not the record. A crash whose fingerprint the app already reported says so, with Dismiss only; one fixed in a newer version says "This is fixed in version F." with Update.
- **The GitHub App can only file issues on one repo.** If the Worker is compromised, an attacker can file issues and nothing else, which stays inside what [ADR 0016](./0016-releases-built-and-signed-on-the-maintainers-machine.md) already accepts: the one thing a compromised credential must never do is ship code, and this one can't. The App's private key and the Cloudflare token live in Bitwarden, never in a file in the repo, and the Worker is deployed from the maintainer's machine. While the repo is public, the issues page is already open to spam; if it goes private, the relay is the only way in, bounded by the rate limit, the schema and the kill switch.
