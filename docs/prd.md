# Unimatrix Zero v1 PRD

Unimatrix Zero is a free desktop app (Electron; Mac, Windows, Linux) that drives the user's existing Claude and ChatGPT subscriptions. Every conversation is a **Tree** that branches at any Reply, shown either as a whole on a canvas or one Thread at a time as a chat.

This document is the v1 spec, assembled from the decisions on the [Unimatrix Zero v1 spec](https://github.com/qodesmith/unimatrix-zero/issues/1) map. It is an index with detail: each section states what was decided and links the ticket that holds the full reasoning. The vocabulary is [`CONTEXT.md`](../CONTEXT.md); the hard-to-reverse choices are in [`docs/adr/`](./adr/). Where this document, a ticket and an ADR disagree, the ADR wins, then the ticket's latest resolution or amendment, then this document.

**Status:** complete except for one live check. Native Windows Sandbox behaviour is written from the vendor docs; the live check is [#58](https://github.com/qodesmith/unimatrix-zero/issues/58), and any correction goes into ADR 0018 by PR.

## 1. Product

**Audience.** A software engineer, a stay-at-home parent and a child should all find it easy. Users never see or need to know about a terminal; no copy mentions a terminal, an install or a CLI. Power users are never artificially limited.

**Money.** Subscription sign-in only, never API keys; it works on the $20 plans (Claude Pro, ChatGPT Plus). No paid developer accounts, no app stores, no user accounts, no paid infrastructure and none the app needs in order to work. Free, stateless, optional services that hold no user data are allowed (the Report relay, [ADR 0017](./adr/0017-reports-go-through-a-stateless-relay-into-github-issues.md)). The app is MIT licensed and the repo is public.

**Terms.** The Claude connection ships regardless of the ambiguity in Anthropic's third-party wording, with T3 Code as precedent. No approval request, no disclosure in the app or README. Providers are pluggable, so a ChatGPT-only user is fully supported. ([Staying within Anthropic's subscription terms](https://github.com/qodesmith/unimatrix-zero/issues/21))

**Precedents.** T3 Code for the subscription approach (wrapping the vendor CLI or SDK) and tldraw for the canvas feel.

**Stack.** Electron, Bun for development only, React, Tailwind and shadcn, SQLite through Drizzle, React Flow for the canvas, TanStack Query and TanStack Store, Streamdown for Markdown. No AI library ([ADR 0005](./adr/0005-no-ai-library.md)).

## 2. Scope

**In v1:** Claude and ChatGPT; canvas mode and chat mode on one Tree; Mac, Windows and Linux; attachments; Workspaces (files the AI edits, app-owned or a linked folder, with Snapshots per Reply); Subagents; MCP servers, Skills and Plugins; Summaries; Export, Archive and restore; full-text search; usage display; Themes (format, built-ins, import/export); Reports.

**Out of scope** (ruled out on the map; a redraw of the destination is a new effort):

- Syncing across devices, any cloud backend, user accounts
- Importing conversations from other apps (Claude.ai, ChatGPT, Claude Code)
- Sharing Trees with other people
- Merging Branches (the AI can combine Branches' files through a Prompt; the Tree stays a tree)
- Providers beyond Claude and ChatGPT
- Mobile; app store distribution
- Kid-specific or parental features
- Regenerate as a sibling Reply; editing a sent Prompt (delete and prompt again)
- Interface languages other than English
- Multiple accounts per Provider, or switching accounts
- Exposing Branches as real git branches in a linked repo
- Automatic archiving or reminders to archive; merging a restored Tree with an existing one or keeping both copies
- Moving the app's data folder to another drive (Archive, then delete)
- User-defined Subagents (name, prompt, tools)
- A Theme editor and in-app Theme gallery
- Theming and visual polish: the final token set, extra built-in Themes, final icon artwork, font bundling, general UI polish (a future effort)

## 3. Conversation model

Canonical in `CONTEXT.md`. The points everything else builds on ([Conversation model and v1 scope](https://github.com/qodesmith/unimatrix-zero/issues/18)):

- A **Tree** is made of **Turns**: a **Prompt** (exactly one user message) or a **Reply** (the AI's whole turn, however many tool calls, Subagents or thinking blocks it contains). A Prompt always follows a Reply except the root, and has at most one Reply.
- **Forks happen only at Replies.** A **Branch** is one direction taken from a Fork. There is no "main" Thread. A **Thread** is one root-to-leaf path: what the AI sees when continuing from that leaf.
- Several Threads can stream at once. A stopped or failed Reply is still a Reply and can be continued or branched from; a failed Reply can be retried in place (recovery, not a Fork).
- Deleting a Prompt deletes it and everything below it. There is no editing.
- **Context size** is the cumulative tokens along a Thread up to a Reply, reported by the Provider, never summed from Turns, and never including a Subagent's own tokens.
- The **Model** is chosen per Prompt; one Thread may pass through several Models and Providers, in the same Tree.

## 4. Connecting a Provider

Source: [Onboarding and sign-in flow](https://github.com/qodesmith/unimatrix-zero/issues/16) (prototype, variant C), [Can sign-in and CLI install be fully hidden?](https://github.com/qodesmith/unimatrix-zero/issues/4), [Ship the vendor programs or use the user's installed copies](https://github.com/qodesmith/unimatrix-zero/issues/20).

- **First launch is one Connections screen.** An intro line ("Talk with Claude or ChatGPT, and branch any conversation into as many directions as you like. It uses the plan you already pay for."), then Claude and ChatGPT side by side as cards (logo, name, "Pro or Max · by Anthropic" / "Plus or Pro · by OpenAI", Connect). "Start chatting →" unlocks once one Provider is connected and opens the empty Tree.
- **Connecting a card** turns it into a checklist: **Get Claude ready** (download with progress, "24 of 100 MB") → **Sign in on Claude's page** (opens the vendor's own page in the browser, with "Claude's page may say "Claude Code". That's normal." and "Don't see the page? Open it again") → **Paste the code** (Claude only, when its page shows one) → **Check your plan**. Cancel is available throughout. One Provider connects at a time. Done: a green card with "Connected", the email and the plan.
- **Mechanics.** The vendor program is downloaded on Connect ([ADR 0008](./adr/0008-app-managed-vendor-programs.md)), so the sign-in page can only open once the download finishes. Claude signs in through the unmodified `claude auth login` with no TTY (the app shows the URL and a paste-code field); ChatGPT through `codex app-server`'s `account/login/start` and the `account/login/completed` notification. Status, email and plan come from `claude auth status` / the SDK's `accountInfo()` and Codex `account/read`. The app never sees or stores a credential. `claude setup-token` is rejected, even as an opt-in.
- **Errors** show on the card in plain words with one action: download failed or offline ("Couldn't get Claude ready. Check your internet connection and try again." → Try again); cancelled or no answer on the vendor page (→ Try again); wrong code (inline); a Claude Free account ("Unimatrix Zero needs Claude Pro or Max." → Use a different account).
- **Later:** the second Provider is connected from Settings → Connections, which shows the same cards. Sign out and Remove are in §18.

## 5. Canvas mode and chat mode

Source: [Canvas mode UX](https://github.com/qodesmith/unimatrix-zero/issues/14) (prototype, variant D), [Canvas engine](https://github.com/qodesmith/unimatrix-zero/issues/19), [ADR 0019](./adr/0019-canvas-is-a-display-for-the-tree.md).

- **Canvas mode is the app.** One canvas holds exactly one Tree, rendered with React Flow. Two orientations share every feature: **vertical** (top-down, the default; Prompt and Reply as separate equal-width boxes) and **horizontal** (left-to-right; one card per **Exchange**, Prompt as header, Reply as body). The toggle animates Turns to their new positions. Orientation is a global Setting; the canvas toggle is a shortcut to it.
- **Chat mode is a slideout** on the right that opens on the Thread of any clicked Turn, can expand to full screen, and has exactly one Input at the end of the shown Thread. To switch Threads, click another Turn on the canvas; there is no Thread switcher. Sending from the slideout into a Reply that already has a response branches, and the slideout follows the new Branch.
- **Layout and navigation.** Layout comes from the Tree: Turns cannot be dragged, Branches read oldest-first. Scroll pans, pinch or ⌘-scroll zooms. On submit the canvas pans to centre the new Reply, keeps the zoom and does not follow it as it grows. A single-Thread Tree keeps its zoom; the first Branch zooms out just enough to show the whole Tree.
- **Thread highlighting.** The active Thread's path to the root is highlighted; hovering a Turn or typing in an Input highlights that path temporarily (typing wins). With the slideout open, its Thread is the default highlight. Focusing a Thread's leaf Input makes it the active Thread (the sidebar's files follow, any selection clears, the slideout closes, the canvas does not pan).
- **Collapse a Branch.** Any Reply with responses folds and unfolds through its Fork pill ("Fork · N Branches"); the toggled Reply stays put on screen.
- **Grouped controls** at bottom-left: minimap, zoom, orientation toggle, and an attention indicator ("N streaming" / "N failed", click to jump to each).
- **Messages.** Long Prompts and Replies scroll inside a capped height with Show more / Show less (a Setting, on by default). A streaming Reply stays on the newest text unless the user scrolls up. Each Reply shows its Context size badge, with the per-Turn size on hover, and an optional Context size meter (a thin bar toward the Model's limit; a Setting, on by default).
- **Delete** from a Prompt uses a hover overlay with an inline confirmation showing the Turn count and "Deleting frees up to X"; nothing shifts. There is no Undo: "This can't be undone." Deleting rewinds the Provider session so the AI never sees deleted Turns ([ADR 0004](./adr/0004-app-keeps-provider-session-data.md), amended).

## 6. The Input: Prompts, attachments, Models

Source: [Canvas mode UX](https://github.com/qodesmith/unimatrix-zero/issues/14), [Switching model and provider within a Tree](https://github.com/qodesmith/unimatrix-zero/issues/10), [Capability tiers and system prompts](https://github.com/qodesmith/unimatrix-zero/issues/9), [Settings and user preferences](https://github.com/qodesmith/unimatrix-zero/issues/22).

- **Where the Input is.** The active Thread always shows its Input; every other Reply reveals one on hover, and a hover Input holding a draft stays until sent or cleared. An empty Tree shows one centred Input that creates the root Prompt. Submitting into a Reply that already has a response branches.
- **Send key** is a Setting: "Enter sends · Shift+Enter adds a new line" (default) or "Enter adds a new line · ⌘/Ctrl+Enter sends".
- **Model picker.** Every Input has one, defaulting to the Model of the Reply it is attached to; a new Tree starts from the last-used Model. Models are listed at runtime from each Provider. Models the current vendor program is too old for show disabled as "Needs an app update" (or "Update available"). A retired Model falls back to the Provider's current default, visibly. A disconnected Provider's Model offers "Reconnect <Provider>" beside the picker. The Thread is never blocked and the Model never changes without the user seeing it.
- **Switching Model or Provider** continues in the same Tree. Within a Provider, the session is kept. To another Provider, the Thread is handed over through one "rebuild session from Thread" path: ChatGPT takes real history through `thread/inject_items`; Claude takes a text replay in one user message. The full Thread is always sent, never cut or summarised. Replies written by another Model get a hidden `[Reply written by <Model>]` label and one app-written line in the System prompt explains it; the user never sees the labels. Thinking never carries over; tool calls and citations become plain text. Every Reply shows a Provider icon and a Model pill.
- **The re-read note.** One inline note above the Input (never a modal), shown only above about 20k tokens, for anything that re-reads the Thread cold: switching Provider, a System prompt change, an expired prompt cache, forking into a new working copy, turning on run commands. Wording talks about the user's limit ("Switching to ChatGPT will re-read ~48k tokens of this conversation (uses more of your limit)."). The estimate is Context size plus setup overhead. A Setting hides the note.
- **Attachments.** An attach button plus paste and drop. Images show as thumbnails with a lightbox; other files as chips (name, size). The Tree keeps every original file (under `userData/attachments/`, named by SHA-256) and converts fresh from it on every hand-over, so losses never pile up. Text-like files go inline as text to both Providers. Claude takes images, PDFs and text inline. Codex takes images only: PDFs reaching ChatGPT go through pdf.js page by page (a text page as text; a page with no text or with images over about 10% of it as an image plus its text), the note says so ("1 PDF sent as text (layout and images not included)"), and conversions are cached. See Appendix A on PDFs attached directly to a ChatGPT Prompt.

## 7. Replies

Source: [Canvas mode UX](https://github.com/qodesmith/unimatrix-zero/issues/14), [What stopping a Reply does upstream](https://github.com/qodesmith/unimatrix-zero/issues/23), [Tree storage and source of truth](https://github.com/qodesmith/unimatrix-zero/issues/11), [AI and chat-UI library stack](https://github.com/qodesmith/unimatrix-zero/issues/12), [Provider drivers, process model and IPC event list](https://github.com/qodesmith/unimatrix-zero/issues/38).

- **Streaming.** Replies render word by word on both Providers, through Streamdown with Shiki, math and Mermaid (loaded only when a Reply contains a diagram), behind one `<ReplyMarkdown>` component. Thinking summaries show live, collapsed, and are never stored. Tool calls, approval cards, file chips and Subagent blocks render inline at the point they happened.
- **Stop** (button and Esc) calls Claude `interrupt()` or Codex `turn/interrupt`, never tears the session down, waits for the turn-ended signal, and on Codex also interrupts every running Subagent. The partial text shown is stored by the app, because the Provider drops the half-streamed part. A stopped Reply is tagged and can be continued or branched from.
- **Failure** keeps the text the Reply had written and says why on its own line: connection lost, limit reached (with the reset time), the Provider program crashed, disk full. The app never retries on its own. **Retry** rewinds the Provider session to before the failed Turn and runs the Prompt again; it is off, with the reason, when the app is offline or the Provider is signed out. Replies left streaming after a crash become `interrupted` and behave like stopped ones.
- **Saved as it goes.** The Reply row is written at start, per finished part, about every second for partial text, and at the end (`complete` / `stopped` / `failed`). A Claude stream that breaks and is silently re-sent replaces the streamed text (`TEXT_REPLACE`) rather than appending.
- **Automatic title.** Written once, after the first Reply finishes, by the smallest Model the first Reply's Provider offers on the user's plan, as a tiny tool-free request outside the Tree. Never regenerated; renaming is final.
- **Not stored, display only:** thinking summaries, durations and timings, "files changed" summaries (computed from Snapshots).

## 8. System prompts, the Tools panel, approvals and YOLO

Source: [Capability tiers and system prompts](https://github.com/qodesmith/unimatrix-zero/issues/9), [Workspaces](https://github.com/qodesmith/unimatrix-zero/issues/24), [Subagents in every Tree](https://github.com/qodesmith/unimatrix-zero/issues/32), [Provider drivers, process model and IPC event list](https://github.com/qodesmith/unimatrix-zero/issues/38), [Electron security posture](https://github.com/qodesmith/unimatrix-zero/issues/39) Q18.

- **Trees are plain by default.** Plain means no files, not no tools: web search, MCP servers, Skills and Subagents still run. A Workspace is an optional property of the Tree (§9).
- **System prompt.** Set per Tree as a copy of the global default; changeable at any time, applying to later Replies with the re-read note. Each Reply records the exact text it ran under (an internal, read-only history). Presets ship read-only: **Default** (a plain helpful assistant, good with Markdown, no mention of agents), **Concise**, **Explain simply**, **Coding helper**; Duplicate makes an editable copy. The library in Settings holds presets, the user's own, and the global default; "Save to library…" on a Tree's panel turns a variant into an entry. Deleting the current default falls back to the Default preset. Both Providers accept a full replacement under subscription sign-in; Claude prefixes one identity sentence of its own and needs `snapshot: false`. Workspace Trees add an app-written **Workspace section** under the System prompt (§9); with run commands on, the vendors' own agent prompts are used with the System prompt appended.
- **What is never loaded** from the user's own setup: user-level `CLAUDE.md` / `AGENTS.md` and user settings (hooks, permissions, model, output style). What can be: the user's MCP servers, Skills and Plugins through the app's own libraries (§17), and a linked folder's own `CLAUDE.md` / `AGENTS.md` (the search up through parent folders is blocked; `.codex/config.toml` is never loaded). Plugin hooks never run.
- **Plain ChatGPT Trees** are locked down in layers because Codex has no clean "no tools" mode: `environments: []`, feature flags off, `approvalPolicy: untrusted` with every request auto-declined, a deny-all `PreToolUse` hook if per-thread hooks load, an empty app-owned `cwd`, and any tool call that still gets through is shown in the Reply. `features.multi_agent` is not part of this; Subagents are controlled by `agents.enabled` (§11).
- **The Tools panel** (per Tree, defaults in Settings → Tools): web search (always on by default), Subagents (on), each MCP server, Skill and Plugin from the libraries (on, except where noted), Claude account connectors (**off** by default: about 30k tokens per cold Turn), the vendors' built-in Skills and Codex's remote plugins (off, listed in a "Built in" group per Provider), and the Workspace permission level. Skills that run scripts are marked "needs a Workspace with commands" on ChatGPT. Toggles apply live with no visible resume dance.
- **The approval card** is inline in the Reply where the tool call happened; the stream pauses there. Allow once / Always allow in this Tree / Deny, with "This happens outside the conversation, so other Branches will see it too." It names the Subagent asking, if any. Once answered it collapses into a chip (✓ allowed / ✕ denied); in canvas mode a waiting Turn gets a badge. The app enforces this on both Providers (Claude `canUseTool` plus `PreToolUse`; Codex per-server `approval_mode` and approval requests). Read-only tools run without asking where the marker exists. Writes inside the working copy are auto-approved; commands inside the Sandbox run without a card (§10).
- **Reviewing additions.** A review screen appears only when an addition includes an MCP server with a local command: one screen per add action, listing `command` and `args`, Skill names, and what was dropped. Changed local-server definitions in a Plugin stay off with a "1 change to review" badge until accepted.
- **YOLO.** One global Setting, off by default, confirmed once when turned on, with a badge beside the Input. It removes approvals and the Sandbox together (Claude `bypassPermissions` with the Sandbox off; Codex `danger-full-access` with `approval_policy: never`). It never widens what a Tree can do: tools that are off stay off, write-only stays write-only, plain stays plain. No per-Tree YOLO; "Always allow in this Tree" covers that.

## 9. Workspaces

Source: [Workspaces](https://github.com/qodesmith/unimatrix-zero/issues/24), [Workspaces: snapshots, working copies and linked folders](https://github.com/qodesmith/unimatrix-zero/issues/25) (amended), [Workspace file tree and canvas](https://github.com/qodesmith/unimatrix-zero/issues/26) (prototype, variant A plus C's chips), [ADR 0010](./adr/0010-linked-folder-holds-one-thread.md).

- **Two independent choices** per Workspace: where the files live (**app-owned**, the default, in `userData`; or a **linked folder** of the user's) and what the AI may do (**Write files**, the default; or **Write files + run commands**). App-owned → linked is a one-way "Move Workspace to a folder…". A plain Tree's empty files area says "Add files to this Tree" with the two options.
- **Every Reply has a Snapshot**: the files as they stood when it finished. A Reply that changed nothing reuses its parent's. Viewing any Turn shows its Snapshot without touching disk. User edits between Replies are caught by a snapshot at the start of each Turn (about 150 ms on 23k files) and recorded as a **User edit** ("Edited by you"); the AI is told. A watcher (`@parcel/watcher` or recursive `fs.watch`, not chokidar) only keeps the UI live.
- **Storage.** One hidden git store per Workspace in `userData`, one index per working copy, never the user's `.git`, no `git worktree`, nothing the user can see. Ignore rules: every nested `.gitignore` and `.git/info/exclude`, read by the app, plus default excludes (`node_modules`, `.venv`, build folders). Every version of every file is kept; files of 100 MB or more live in a per-Workspace folder named by hash with a pointer in the Snapshot, placed in working folders as copy-on-write clones or full copies, never links. The app never deletes data on its own (§15).
- **Working copies.** One per Thread that is not in the folder, created on the first Prompt sent into it (viewing never creates one), reused as the Thread continues, deleted when its leaf is deleted or its Thread moves into the folder, never evicted. Ignored files reach a new working copy by a copy-on-write clone where the filesystem allows, otherwise a capped copy of small ignored files, plus an optional per-Workspace **Setup command** (run commands only; the user's own command, outside the Sandbox). The Workspace section tells the AI what is missing. Forking into a new working copy is a cold Turn on both Providers (the re-read note).
- **Linked folders.** The real folder holds exactly one Thread. Linking snapshots it as it is, uncommitted edits included; the user's staging area, branch and `git status` are never touched. Non-git folders are allowed with default excludes and a size cap; folders still too large after excludes (around 50k files) are refused with a plain explanation. The folder changes Thread only through **"Put this Thread in the folder"** (snapshot first, replace, never merge), or the per-Workspace setting **"Keep the folder in sync with the selected Thread"** (off by default; waits for a generating Reply, with a note). Hand edits caught by a swap become a User edit on the outgoing Thread.
- **Permissions.** Writes inside the working copy are auto-approved on both kinds (Claude's five file tools with `acceptEdits`; Codex `workspace-write` with `shell_tool` off and temp excluded); writes outside go to the card. Other Branches' files and the hidden store are a hard deny without asking. Overwriting User edits is prevented by both Providers refusing edits to files changed since last read, and by Snapshots. Commands each go to the card unless the Sandbox covers them (§10). Turning on run commands mid-Tree applies to the whole Tree from then on, with the re-read note.
- **The Workspace section** of the prompt is app-written, never a Setting, under about 400 tokens: the working folder and that it is the only place to write, the permission level, how to read another Branch's files when asked to combine them (read-only paths), the User edits since the last Reply. The prompt explains; code enforces.
- **File tree and canvas.** One sidebar: Trees above, a view-only file tree ([@pierre/trees](https://trees.software/)) below that follows the Turn selected on the canvas (else the active Thread's leaf), coloured by what that Reply added, changed or deleted. No folders mirroring the Tree, no Segments. A Reply lists the files it changed and the commands it ran as **chips** under its text; clicking a chip opens the file as it was at that Reply. The Files header says only where the files live (a linked folder's path, cut at 60% with a tooltip; no badge for app-owned).
- **Opening files.** At a Thread's leaf (the only version on disk): Open in default app and Reveal in Finder. At earlier Turns: Open this version and **Save a copy…** (a one-time copy of that Reply's files to a chosen folder). Open is refused for files with the executable bit; HTML defaults to the in-app preview with Open in browser as the explicit choice; Open in editor uses an editor main detected, offered for linked folders first.
- **Previews**, in three tiers: in the app (images, audio, video, PDF via pdf.js, Markdown through the same hardened pipeline as Replies, CSV as a table, code and text detected from bytes), the OS (Quick Look on macOS for Office and the like, OS thumbnails and icons), and a fallback card. Long text previews its start; very large files are not previewed; files stream through `uzfile://` with range requests. The security rules for each type are in [ADR 0014](./adr/0014-electron-security-posture.md).

## 10. The Sandbox

Source: [Vendor sandboxing for commands the AI runs](https://github.com/qodesmith/unimatrix-zero/issues/49), [Live tests](https://github.com/qodesmith/unimatrix-zero/issues/53), [Sandbox edges](https://github.com/qodesmith/unimatrix-zero/issues/56), [Check what Cowork and ChatGPT desktop let a command reach](https://github.com/qodesmith/unimatrix-zero/issues/55), [ADR 0018](./adr/0018-commands-run-inside-the-vendor-sandbox.md).

- **The card decides whether a command runs; the Sandbox decides what it can reach.** Every command in a run-commands Workspace runs inside the vendor's Sandbox, set to what that vendor's desktop app does. Write files Workspaces have no shell and nothing to sandbox.
- **Codex:** `workspace-write`, network off, approvals `on-request`. **Claude:** the SDK `sandbox` option with writes allowed only in the working copy, temp and the package caches; a credentials deny list (`~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.kube`, `~/.gnupg`, keychains, the app's own Provider folders) mirrored as Read-tool deny rules; network default-deny with an empty allowlist. Reads are the whole disk minus credentials on both (the one place we differ from Cowork, which runs in a VM). Other Branches' working copies and the hidden store are on the deny list. Subagents inherit the parent's Sandbox.
- **Inside the Sandbox, no card.** Cards remain for everything the Sandbox does not cover: the fence itself, the Read deny rules, file tools outside the working copy, web fetch, MCP servers.
- **At the fence, one card family.** A blocked path or connection makes the Model ask to run outside (Claude's `dangerouslyDisableSandbox` retry, Codex's escalation); the card says the command would run outside the Sandbox, and its "Always allow" covers only that form. Claude's blocked connection also arrives as a `SandboxNetworkAccess` prompt naming the host; its "Always allow" is the per-host rule. Every Bash allow rule the app writes is paired with the ask rule `Bash(dangerouslyDisableSandbox:true)`, or the retry would be approved silently. No built-in allowlist in v1. The standard per-user package caches (bun, npm, pnpm, yarn, pip, cargo, the OS cache folder) are writable on both so installs stay inside.
- **Linux** gets bubblewrap and socat as app-managed helpers beside the vendor programs, first on Claude's `PATH`; Codex brings its own. The app probes before each session (`bwrap --unshare-user --ro-bind / / true`) and starts the Sandbox off when the probe fails.
- **Where the Sandbox is unavailable** (native Windows on both vendors; Linux where bubblewrap cannot run), commands still run and the user is told once when turning on run commands, with the Tools panel saying so while it is on. Claude runs with the Sandbox off; Codex with `danger-full-access` and `approval_policy: untrusted`, so losing the floor does not also remove the cards. **Windows position: from docs, verification pending** ([#58](https://github.com/qodesmith/unimatrix-zero/issues/58)).
- **YOLO** removes approvals and the Sandbox together (§8).

## 11. Subagents

Source: [Subagents on both Providers](https://github.com/qodesmith/unimatrix-zero/issues/31), [Subagents in every Tree](https://github.com/qodesmith/unimatrix-zero/issues/32).

- **On by default in every Tree**, as a Tools-panel entry with a global default. Off means no `Agent` tool on Claude and `agents.enabled = false` on Codex. One line of help: "Subagents can use your plan's limits faster."
- **A Subagent can do exactly what its Tree allows**: in a plain Tree web search plus the MCP servers, connectors and Skills that are on; in a Workspace the Workspace level too, with several Subagents allowed to write to the working copy at once (the subagent section asks the AI to split work by file). Approvals use the same card, naming the Subagent. Provider defaults for concurrency (Claude 20 at once, 3 deep; Codex 3 at once); the AI may pick each Subagent's Model.
- **Subagent work stays inside one Reply.** Claude Subagents run in the foreground (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`) with the built-in agent types off; one app-written general Subagent runs under the Tree's System prompt plus a short subagent section. Codex children carry the Tree's System prompt plus Codex's own multi-agent text. A Reply finishes only when the parent and every Subagent have finished; Stop interrupts all of them; the Snapshot is taken after.
- **Display.** On the canvas a Reply shows "3 subagents · 2 running", then a "3 subagents" chip; clicking opens chat mode at that Reply with the block expanded. In chat mode a collapsible "Subagents" block, collapsed by default: one row per Subagent (task line, or "Subagent N" on Codex where the task text is encrypted; Model pill; status; tokens), expanding to the final result, with "Show steps" for tool calls and messages; nested Subagents indented. A failed Subagent does not fail the Reply. Subagent tokens are shown per row and never added to Context size.
- **Storage and Exports.** Each Reply stores the row data; the live progress stream is not stored. Subagent transcripts are part of the Provider session copy, so they go into Archives and are deleted with their Reply. Forking at a Reply that used Subagents uses the native fork; the Branch remembers results but cannot resume them. Replay to another Provider includes final results as plain text. Exports get one `<details>` block per Subagent under its Reply.

## 12. Sidebar, Collections and search

Source: [Tree sidebar](https://github.com/qodesmith/unimatrix-zero/issues/34) (prototype, variant B, amended), [Export, Archive and Summary entry points](https://github.com/qodesmith/unimatrix-zero/issues/30), [Full-text search](https://github.com/qodesmith/unimatrix-zero/issues/43), [⌘K search](https://github.com/qodesmith/unimatrix-zero/issues/44) (prototype, variant A), [Usage and limit display](https://github.com/qodesmith/unimatrix-zero/issues/36), [App name, sidebar label and visual identity](https://github.com/qodesmith/unimatrix-zero/issues/33).

- **Layout.** Three resizable sections, VS Code Explorer style: **Trees**, **Files** (§9) and **Usage** (§16), with draggable dividers (double-click resets) and collapse to header. Minimum heights 120 / 180 / 90 px. Sidebar width 290 px (default and minimum) to 640 px. Width, splits and collapsed state survive switching Trees and launches. The gear opens Settings. The UI calls them "Trees"; the empty state says "Start a new Tree" with a one-line explanation.
- **Rows.** Title (the root Prompt's first line in italic until the automatic title arrives), relative time, a dot while a Reply streams, a red dot for an unseen failure. Renaming by double-click, F2 or ⋯ → Rename is final. The **⋯ menu**: Rename, Storage…, Summarize this Tree…, Export Tree…, Archive…, Move to Collection…, Delete…. It floats anchored to its row.
- **Collections.** One level, user-made, 📁 icon, never called folders ("New Collection", "Move to Collection…", "Rename Collection", "Delete Collection"; deleting one returns its Trees to the top level). Trees go in by drag or the menu. No pins. Sort menu: Last active (default), Date created, Name. ⌘/Shift-click selects several for Move to… or Delete….
- **Deleting** one or several Trees asks with the Turn count, Workspace versions deleted, a note that a linked folder stays put, "Deleting frees up to X", and "Archive first…".
- **Search** is a ⌘K palette (or "Search all Trees") over titles, Prompt text, the visible text of Replies and attachment file names, using SQLite FTS5 (`unicode61 remove_diacritics 2`, prefix match per word, every word must match in the same Turn or the title; queries under 3 characters and Chinese/Japanese fall back to a plain scan). Not indexed: thinking, tool calls and output, Subagent work, Workspace files, System prompts. Prompts index when sent, Replies once when finished; triggers keep deletes and restores in sync and are recreated after every migration.
- **The palette.** Empty: "Recent", up to 8 Trees (last opened from search first, then by activity), persisted between launches. Results: one row per Tree (title with matches marked, Collection, Provider dots, last active, one snippet from the best match labelled "You" or "Reply" with a Model pill), "▸ N more in this Tree" expanding inline. Ranking: title match, then how many Turns match with diminishing weight, then recency; a sort menu offers Last active and Date created. Filter chips: Titles only, Collection, Provider, Date. Keyboard: ↑↓, → expand, ← back, Enter open, Esc close. Opening a result opens the Tree with the chat slideout on that Turn, with only that Turn's matches marked on the canvas and in the slideout; Esc clears the marks.

## 13. Summaries

Source: [Summaries](https://github.com/qodesmith/unimatrix-zero/issues/28), [Export, Archive and Summary entry points](https://github.com/qodesmith/unimatrix-zero/issues/30).

- **Made outside the Tree:** no Turn, no Fork, never seen by the AI later. **Thread summary** covers the root to any Reply ("Summarize up to here…" in the Reply ⋯ menu, canvas and chat mode, not on streaming or failed Replies). **Tree summary** covers the whole Tree ("Summarize this Tree…" in the Tree menu). Throwaway: Copy or Save as Markdown (with a header: Tree title, Model, date, the Reply covered); never stored or archived; not an Export.
- **Two Summary prompts** (Thread, Tree) in Settings → Chat, editable with Reset to default; not in the System prompt library.
- **How it runs.** A Thread summary defaults to the Reply's Model and forks that Reply's Provider session (cached prefix, sees attachments and tool results), then discards the fork; another Model falls back to sending the Thread as text with the re-read note. A Tree summary is a fresh tool-free session, defaulting to the last-used Model, fed the outline Export (§14).
- **Big Trees** are split by the app in the main process, cut at Forks: the root run first, each child run with its parent's summary as context, runs at the same depth in parallel (at most 3 at a time), every Turn read exactly once, then a combining pass in Tree order. A Thread summary sent as text to a smaller-window Model is chunked in order. The start dialog says "Reads ~N tokens, in M parts". A failed piece stops the run with Retry and no partial Summary.
- **The panel** is non-modal, floating bottom-right over the canvas: title and Model, progress ("3 of 7 parts read, 3 at a time", "Combining parts…"), the text streaming in, Stop (Esc) while running, Copy and Save as Markdown… after. Close asks "Discard this summary?" only if it was neither copied nor saved.

## 14. Export, Archive and restore

Source: [Exporting and restoring Trees](https://github.com/qodesmith/unimatrix-zero/issues/27), [Export, Archive and Summary entry points](https://github.com/qodesmith/unimatrix-zero/issues/30) (prototype, variant A), [ADR 0011](./adr/0011-archives-are-their-own-versioned-format.md).

- **Exports are one-way Markdown.** Export Thread (Reply menu): one linear `.md` from the root to that Reply, with a preview, Copy and Save…. Export Tree (Tree menu): **one outline file** (default; Branches as nested headings) or **one file per Thread** (a folder named after the Tree, files `NN - <first words of the leaf Prompt>.md`, depth-first). Content: title and date, Prompts as **You**, Replies by Model, stopped/failed markers in italics, attachments as `📎 filename`, tool calls as one line, changed files by name, Subagents as `<details>`, the System prompt only with "Include System prompt", no thinking. Both dialogs say an Export cannot be restored. Copy as Markdown is in the Reply menu. No raw text or JSON exports.
- **Archives** are the app's own versioned zip of JSON documents plus the files they need: every Turn, attachments by hash, each Workspace's hidden store as a git bundle plus its large-file folder, Provider session data as opaque files. **Archive…** (Tree menu) holds one Tree; **Archive everything…** (Settings → Archive & restore) adds Settings, the System prompt library and user Themes. Never sign-ins or user-supplied values such as MCP tokens; ignored files are not archived. The dialog lists what is inside with sizes and a total, says "sign-ins are never included", and runs the fit check first. Building re-hashes every file. Manual only.
- **Restore** starts from Settings → Archive & restore, dropping an Archive anywhere on the window ("Drop to restore" overlay) or double-clicking the file. The preview, shown before anything is written, groups **Will be added**, **Different from yours** and **Already here, skipped**; each differing Tree gets **Keep mine** / **Use archived** with what each discards; Use archived that deletes Turns gets a delete-style confirmation; "Also use the Settings from this archive" is unticked and shown only for Archive everything files; size and free space are shown and Restore is blocked if it does not fit. Ids are kept. A newer app upgrades older Archives in code; an older app refuses a newer one with "This archive needs a newer version of the app". Linked folders: if the Thread in the folder survives the link stays and the next snapshot records differences as a User edit; otherwise the folder is unlinked with its files untouched; a linked Tree restored elsewhere comes back unlinked, and "Link a folder…" accepts only a new or empty folder. Restored hidden stores are rebuilt from objects and our own refs only ([ADR 0014](./adr/0014-electron-security-posture.md)).

## 15. Disk usage

Source: [Disk usage and low disk space](https://github.com/qodesmith/unimatrix-zero/issues/29), [ADR 0010](./adr/0010-linked-folder-holds-one-thread.md).

- **The app never deletes data on its own.** Stored data goes only when the user deletes what it belonged to, and cleanup after a deletion never blocks: unreferenced Provider session data, working copies whose leaf is gone, Snapshot refs of deleted Replies (occasional `git gc`), unreferenced attachments, provider-side sessions best-effort through official APIs only.
- **One figure per Tree, "Deleting frees up to X"**: only data the Tree alone owns (its Turns, Provider session data, attachments no other Tree uses, cached conversions, its hidden store at real compressed size, large-file versions, working copies at full size). Linked folders are never counted or touched. Deleting a Branch frees its unique data too, with the same figure.
- **Where:** Settings → Storage (the app's total, free space, every Tree by size with Delete / Reveal, and an off-by-default "Show breakdown" switch: Messages, Provider sessions, Attachments, Converted attachments, File history, Large files, Working copies), "Storage…" in the Tree menu, and the figure in delete confirmations. Nothing in the sidebar.
- **Low disk** (under 5 GB or 5%, whichever is smaller; the app's disk plus a linked folder's disk): a dismissible band "Your disk is almost full (X left). See what's using space →". **Critical** (under 1 GB): the band cannot be dismissed, and new working copies, "Put this Thread in the folder", Archives, restores and vendor program downloads are blocked; Replies keep running. If the disk fills mid-Reply the Reply fails like any other, keeping its partial text; a Snapshot that cannot be written marks the Reply "Files not saved for this Reply".
- **Fit checks** (size plus 1 GB) before Archive, restore, a new working copy, "Put this Thread in the folder" and vendor downloads, refused before anything is written, with one sentence and one action; Archives also offer saving to another drive.

## 16. Usage and limits

Source: [What usage data each Provider reports](https://github.com/qodesmith/unimatrix-zero/issues/35), [Usage and limit display](https://github.com/qodesmith/unimatrix-zero/issues/36) (prototype, variant D), [Reconnect, offline and error states](https://github.com/qodesmith/unimatrix-zero/issues/40) follow-up.

- **Where.** The sidebar's Usage section lists every window each Provider reports, named by length (5-hour, Daily, Weekly, Monthly), with freshness and ⟳ Refresh, and "No limits reported" where there are none; collapsed, its header shows one ring per Provider for its fullest window. A ring beside the Model pill in every Input shows the tightest window limiting the picked Model (per-model weeklies count only when that Model is picked) and from 80% spells it out ("82% of 5-hour · resets 6:20pm"). Settings → Connections shows every window with reset time and countdown.
- **Sources.** Claude: `rate_limit_event` per Turn (5-hour and 7-day in `unifiedWindows`) and the experimental on-demand `get_usage` on an open session, with per-model weeklies and the "On usage credits" state. Codex: `account/rateLimits/read` on demand and `account/rateLimits/updated` during Turns, with 0, 1 or 2 windows. If `get_usage` disappears, the app shows the last `rate_limit_event` ("From your last Reply, X ago") without per-model weeklies. ChatGPT credits are not shown in v1.
- **Refreshing** on open, on connect, on ⟳ and periodically, plus the pushes during Turns, without ever starting a process only to probe (see Appendix A). After 10 minutes a figure is marked stale; offline it says "Couldn't refresh · updated X ago".

A refused Reply keeps its partial text with "Limit reached · back at 12:40pm" and **Retry with <other Provider's Model>**, then a plain Retry after the reset. Limits are per account, so every Thread on that Provider waits; a refused request also brings the real figure back.

**Principle.** An option earns a Setting only when reasonable users want either value and the default is known. Visual and behaviour Settings are global, never per Tree; anything shaping what the AI does in a Tree lives on the Tree, and Settings holds only the defaults new Trees start from. ## 18. Offline, reconnect and error states

Source: [Reconnect, offline and error states](https://github.com/qodesmith/unimatrix-zero/issues/40) (prototype, variant A), [Provider drivers, process model and IPC event list](https://github.com/qodesmith/unimatrix-zero/issues/38) (amended).

- **Bands across the top of the canvas** for problems affecting the whole app or a whole Provider: offline, an expired sign-in, a Provider program that will not start, an outage, a failed update, low disk, a crash. Worst first, each with one action, overlaying the canvas so nothing jumps.
- **No offline queue.** Offline, Send is off, the draft is kept ("Offline · sending waits for the connection"), and deleting still works. **A refused send adds nothing to the Tree**: the Prompt stays in the Input and the band says why ("Sign in again", "Download Claude again"). While a Provider host restarts, Send is off until it reports ready; the app never holds a Prompt and sends it later by itself.
- **Cut-off Replies** keep their text ("reconnecting…" then "Connection lost") and are never retried by the app (§7).
- **Sign-in expiry** is expected roughly every 4 weeks on Claude. "Login expired" and "token revoked" become the reconnect band; "Sign in again" opens a dialog with the onboarding steps; signing in as a different account simply continues the existing Trees. Refreshing stays with the vendor programs; the app only sees signed in or out, never runs `claude auth status` on a timer or throwaway sessions, and closes `claude` processes gracefully.
- **A broken Provider program:** "Download Claude again" with "Downloading Claude… N%"; if a fresh copy still fails, "Report a problem…". **A failed update** says it "didn't finish downloading" or "didn't pass its safety check", that the current version still works, and offers Try again.
- **Settings → Connections:** **Sign out** ("Ends your sign-in. Claude stays set up; sign in again to pick up where you left off."; asks first only while Replies run) and **Remove Claude…** ("Removes Claude from this app. Your Trees stay. You can download Claude again later."; always asks, shows how many Replies are running, stops them with "Stopped: you removed Claude", cancels any download, deletes the sign-in data and the vendor program, and returns the card to Connect). "Disconnect" is not a word the app uses.

## 19. Reports and Diagnostics

Source: [Crash and bug reporting without PII](https://github.com/qodesmith/unimatrix-zero/issues/47), [ADR 0017](./adr/0017-reports-go-through-a-stateless-relay-into-github-issues.md).

- **"Report a problem…"** shows a picker, an optional description (required when there is no error; at most 2,000 characters, fenced and treated as untrusted), a "What's included" list and "Show exact text", then Send, then "Sent as #123". Nothing is sent without that preview and click; there is no "Always send" and no telemetry.
- **The channel.** Main posts the Report to one Cloudflare Worker that validates it with the shared schema, files it through a GitHub App with `issues:write` on this repo only, labelled `needs-triage`, and keeps nothing (logs off; the IP only as a rate-limit key for the request). Fallback: copy the Report and open a pre-filled GitHub issue; offline, Copy only. The manifest's `reports` field is the kill switch.
- **No identifiers and no free content.** A random id per Report; every other field is a version, an enum value, an integer or a stack frame from the app's own code. Never a title, name, path, Setting value, conversation content or vendor message text. The fingerprint is the error code, else class plus top module and function. The app sends at most once per fingerprint per version; the Worker rate-limits per IP; matches update an Occurrences tally, and a match on a fixed issue from a newer version opens a regression issue.
- **Crashes** are detected with the app's own launch marker and structured records, never Electron's `crashReporter`: a renderer crash shows its band at once, a main crash on the next launch, a Provider host crash once restarts reach manual Reconnect. One band at a time; non-fatal errors never prompt. The manifest's `fixed` list drives "Your report #123 was fixed" in the what's-new screen after an update and "This is fixed in version F" on a crash band.
- **Diagnostics** hold schema entries only, in `userData/logs`, trimmed at 14 days or 5 MB, never archived; Copy, Export and Clear in Settings → Updates & About. A separate record of sent Reports outlasts them. Builds are unminified with modules as separate files; source maps stay on the maintainer's machine.

## 20. Distribution, updates and vendor programs

Source: [Distribution and update strategy](https://github.com/qodesmith/unimatrix-zero/issues/13), [Unsigned distribution research](https://github.com/qodesmith/unimatrix-zero/issues/5), [Ship the vendor programs or use the user's installed copies](https://github.com/qodesmith/unimatrix-zero/issues/20), [App name, sidebar label and visual identity](https://github.com/qodesmith/unimatrix-zero/issues/33), ADRs [0006](./adr/0006-unsigned-distribution.md), [0007](./adr/0007-thin-shell-signed-app-bundles.md), [0008](./adr/0008-app-managed-vendor-programs.md), [0012](./adr/0012-stable-identity-separate-from-display-name.md), [0016](./adr/0016-releases-built-and-signed-on-the-maintainers-machine.md).

- **Unsigned.** Ad-hoc signed on Mac, unsigned on Windows and Linux, published to GitHub Releases with a GitHub Pages download page. The page detects the OS, puts that OS's download first (Mac: universal by default, with Apple Silicon and Intel alternatives remembered in `localStorage`), shows first-launch steps with screenshots (Mac Open Anyway; Windows SmartScreen More info → Run anyway; Linux chmod), a "Windows won't open it?" section for Smart App Control (accepted as a loss), and a "Using a terminal?" section. The README links to it.
- **Files shipped.** Mac: `.dmg` for arm64, x64 and universal, plus `install.sh` (curl, no quarantine, no Open Anyway; SHA-256 from the manifest; arch from `sysctl`). Windows: x64 per-user one-click NSIS (`install.ps1` only if PowerShell downloads prove to avoid SmartScreen). Linux: x64 AppImage, installed by `install.sh` into `~/.local/bin` with a menu entry, also offered directly. No `.deb`/`.rpm`, no portable `.exe`, no MSI.
- **Thin shell and signed app bundles.** The installed app is a small Electron shell whose loader runs the app code from a versioned, Ed25519-signed bundle in `userData`, listed in a signed manifest on GitHub Pages (monotonic `sequence`, `expires` about 30 days out, each bundle's source commit, `minShell`, hashes, vendor program versions, `reports`, `fixed`). The loader verifies the signature on every launch; falls back to the last known good bundle, then the copy built into the shell; a bundle is "good" once the database opened, migrations ran and the window rendered, and a bundle that never gets there rolls back with the pre-migration backup restored. First launch fetches the latest compatible bundle before showing the UI (about 5 s, then the built-in copy). On Mac the shell's unchanging `cdhash` keeps privacy grants across app-code updates; a first launch outside `/Applications` calls `moveToApplicationsFolder()`.
- **Updates.** The app checks the manifest on launch and every few hours (a Setting). "Update available" pill with Download and a "What's new" link; nothing downloads until the click; then "Restart to update". Code is never swapped mid-session. Restarting into a newer bundle shows what's new once. Shells ship only for high/critical Electron or Chromium fixes, to stay on a supported Electron major, or when a bundle needs a newer shell: Mac shells replace their own `.app`; Windows and Linux use electron-updater's `generic` provider at the manifest's `shell-N` tag with the download hashed against the manifest. Versioning is one product version (`v1.8.2`) plus a shell generation (`shell-3`, 3.0.0 for electron-updater); About shows "1.8.2 (shell 3)". A failed verification shows "This update couldn't be verified. Reinstall from [download page]."
- **Vendor programs.** Exact, unmodified `claude` and `codex` builds are downloaded on Connect from the vendors into `userData`, hash-checked against the manifest, never re-signed, never taken from the user's PATH, each with its own `CLAUDE_CONFIG_DIR` / `CODEX_HOME` (`settingSources: []`, auto memory off, self-updaters off). Codex is a folder, not a file. Users who already use the CLIs sign in once more. Versions move with app bundles: a weekly CI job bumps the SDK and Codex, regenerates the types, runs smoke tests (including the MCP OAuth smoke) and opens a PR; new programs download with their bundle before "Restart to update"; the previous version is deleted once the new bundle is good. No custom-binary Setting, only a developer-only environment variable.
- **Identity.** "Unimatrix Zero" is the shipped name; `appId` `com.qodesmith.unimatrixzero`, `userData` folder `unimatrix-zero` (set by the shell's loader), Archive format id `unimatrix-zero-archive` and Linux binary `unimatrix-zero` never change.
- **Secrets.** The app never stores or handles Provider credentials and uses no keychain or `safeStorage`. User-supplied values such as MCP tokens are stored as plainly as the vendor tools store them, and never archived.

## 21. Architecture

Source: [Tree storage and source of truth](https://github.com/qodesmith/unimatrix-zero/issues/11), [SQLite + Drizzle research](https://github.com/qodesmith/unimatrix-zero/issues/8), [AI and chat-UI library stack](https://github.com/qodesmith/unimatrix-zero/issues/12), [Provider drivers, process model and IPC event list](https://github.com/qodesmith/unimatrix-zero/issues/38), [Electron security posture](https://github.com/qodesmith/unimatrix-zero/issues/39), ADRs [0001](./adr/0001-app-owns-the-tree.md) to [0005](./adr/0005-no-ai-library.md), [0013](./adr/0013-utility-process-per-provider-main-is-the-hub.md), [0014](./adr/0014-electron-security-posture.md), [0015](./adr/0015-types-derive-from-schemas-ipc-contract.md).

```text
renderer (React, React Flow, TanStack Query + Store)
  │  window.uz = { send, subscribe, registerDroppedFile }   one typed channel, Zod-validated
main (SQLite via Drizzle, hub, saves then forwards, SNAPSHOT on connect)
  ├── Provider host: Claude   (utility process; Claude Agent SDK → claude)
  └── Provider host: ChatGPT  (utility process; app-server JSON-RPC client → codex)
```

- **Storage.** The app's SQLite database (`userData/data/unimatrix.sqlite`, `node:sqlite` through Drizzle 1.0 rc, better-sqlite3 13 as fallback, WAL, main process) owns every Tree; history is rendered only from it. Provider sessions are disposable copies: continue resumes, branch uses the native fork at that Reply (Claude `resume` + `resumeSessionAt` + `forkSession`; Codex `thread/fork` with `lastTurnId`), anything else goes through the one "rebuild session from Thread" path (exact restore from the app's own opaque copy of the session, silently; else Codex `inject_items`; else text replay, the last two with the re-read note). Deleting rewinds the session (Codex `thread/revert`; Claude `resumeSessionAt` on the next continue). Schema: separate `prompts` and `replies` tables (Forks only at Replies), Reply content as ordered provider-neutral JSON parts plus Provider, Model, status, System prompt reference, session coordinates and Context size; `system_prompts` append-only by hash; attachments on disk by hash; `settings`, `themes`; Workspace columns and `working_copies`; FTS5 tables with triggers. UUIDv7 ids everywhere. Migrations run on start behind a backup (keep 3) and a foreign-key guard; a database written by a newer app is refused.
- **Drivers.** One `ProviderDriver` interface per Provider (one account each): connection, `listModels`, `readUsage`, `startReply` → events, `stop`, `answerApproval`, `forkSession`, `rebuildSession`, `rewindSession`, `runOneShot` (titles, Summaries), `mcpSignIn`, and `capabilities` flags (`pdfAttachments`, `skillScriptsInPlainTrees`, `mcpOAuth`, `sseMcp`, `sessionFromTranscript`, …). **The UI branches on capabilities, never on the Provider's name.** Warm sessions close after 10 minutes idle (at most 6 warm Claude sessions); Claude sessions run in streaming-input mode. Each driver runs in its own utility process, started when its Provider is connected, restarted on crash with backoff (1 s, 5 s, 30 s, then manual), the in-flight Reply saved as failed with its displayed text.
- **Events** on one channel, every Reply event carrying `treeId`, `replyId` and an optional `subagentId`, with AG-UI names: `RUN_STARTED`, `TEXT_DELTA`, `TEXT_REPLACE`, `REASONING_DELTA` (display only), `TOOL_CALL_START/ARGS/END`, `TOOL_RESULT`, `APPROVAL_REQUESTED/RESOLVED`, `SUBAGENT_STARTED/FINISHED`, `FILES_CHANGED`, `TOKENS`, `CONTEXT_COMPACTED`, `RUN_FINISHED` (status and failure). Provider events: `PROVIDER_STATUS`, `USAGE_UPDATED`, `MCP_SERVER_STATUS`, `MODELS_CHANGED`, `SIGN_IN_STEP/FINISHED`. The list grows with new event types rather than overloaded ones. The contract is Zod schemas and its own source of truth; main maps rows to it.
- **MCP, Skills, Plugins.** Passed per session (Claude `mcpServers` with `strictMcpConfig`; Codex per-thread `config.mcp_servers`, stdio and HTTP only). MCP sign-in without a terminal on both (Claude's `mcpAuthenticate`, guarded by the weekly CI smoke; Codex `mcpServer/oauth/login` with file credential storage); the vendor programs own the tokens; servers are passed under stable ids. Skills from any folder (Claude `plugins` / config-folder skills; Codex `skills/extraRoots/set`); in plain ChatGPT Trees, user-picked Skills go in as `{type:"skill"}` and AI-picked ones through an app-owned `read_skill` MCP tool. Plugins are unpacked into their Skills and MCP servers; hooks never run. The login-shell environment is read once per launch for `PATH` and `${VAR}` values.
- **Security** ([ADR 0014](./adr/0014-electron-security-posture.md)). Hostile: Reply content, previewed files, Archives/Themes/Skills/Plugins, the network; other same-user programs are out of scope. One window type with every `webPreferences` value explicit, never navigates, denies new windows and webviews; links open externally for `http`, `https` and `mailto` only; nothing from a Reply makes a request without a click (remote images are click-to-load chips through main); CSP as a header with no http sources and a session-level backstop; `app://` serves only the verified bundle and `uzfile://` serves files by id with `sandbox` and `nosniff`; HTML previews in an `allow-scripts`-only iframe; pdf.js, Mermaid strict, KaTeX untrusted; fuses off for RunAsNode, `NODE_OPTIONS` and inspect; no DevTools in production; vendor environment stripped of `ANTHROPIC_*`, `CLAUDE_*`, `OPENAI_*`, `CODEX_*` for correctness; every app `git` call ignores system and global config with hooks off; `userData` is owner-only; no secret ever in a command-line argument.

## 22. Repo, build, test and release

Source: [Repo layout, build toolchain and testing strategy](https://github.com/qodesmith/unimatrix-zero/issues/41), [ADR 0016](./adr/0016-releases-built-and-signed-on-the-maintainers-machine.md).

- **Layout.** A Bun-workspaces monorepo: `shell/`, `app/main/`, `app/preload/`, `app/renderer/`, `app/provider-host/` (`claude/` and `chatgpt/` entries), `shared/contract/`, plus the Report Worker beside the contract. Isolated installs; `tsc -b` project references enforce boundaries; Cerebro-style deep modules (`src/modules/<name>/main.ts`, lint-enforced; `.tsx` only under `ui/`; tests beside their unit). Drizzle stays in main.
- **Build.** Vite 8 everywhere, fully bundled: main and hosts as ESM, preload as one self-contained CJS file, shell as CJS. electron-builder 26.x and electron-updater in `shell/` with an exhaustive fuse config. `bun run dev` runs the renderer through `app-dev://`, watch-builds the rest, restarts Electron or a single host on change, with per-worktree ports and data folders and a `--fake` driver.
- **Tests.** Vitest in two projects: node (contract, main, hosts, shell; database tests under Electron's own Node) and renderer in browser mode. A runtime-match check pins Electron's Node and SQLite versions. Fakes only at boundaries; real in-memory SQLite with migrations. Provider layers: a fake `ProviderDriver`; NDJSON transcripts recorded at the process boundary and replayed by fake `claude`/`codex` binaries (the weekly bump fails if they no longer match); live tests local and opt-in only. Playwright E2E on a test build (onboarding; send, stream, Stop, Fork; a Workspace write; update and Restart; bundle rollback after a failed migration). Packaged smoke of the real fused artifacts, which also checks real shells reject the test key.
- **CI** checks and never ships: format, lint (oxlint type-aware, zero warnings), typecheck (TypeScript 7), knip; unit, E2E and smoke on Mac arm64, Mac x64, Windows x64 and Linux x64; the weekly vendor bump; Electron advisories. No git hooks.
- **Releases** are built and signed on the maintainer's Mac by `bun run release`: preflight with a reviewed diff since the manifest's source commit, local build and tag, live tests against the exact `.asar`, draft upload, CI smoke by manual dispatch, sign the manifest with the key read from Bitwarden into memory, push the tag, publish, push the manifest to Pages. Shells embed the newest published signed bundle.

## Appendix A. Reconciled readings

Two pairs of decisions touch the same point with different words. The reading below keeps both consistent and is what the sections above say; neither needs a decision session, but the maintainer should confirm them when splitting implementation issues.

1. **PDFs attached directly to a ChatGPT Prompt.** [Capability tiers and system prompts](https://github.com/qodesmith/unimatrix-zero/issues/9) said a PDF attached in a plain Tree with ChatGPT is disabled with an explanation (copied into the Workspace in a Workspace Tree). The later [Switching model and provider within a Tree](https://github.com/qodesmith/unimatrix-zero/issues/10) added a pdf.js conversion for PDFs that reach ChatGPT on a hand-over, with the original kept and a note. Reading: the conversion applies to any PDF that reaches ChatGPT, attached directly or handed over, so the attach option is never disabled and the Tree always keeps the original. The Workspace copy from #9 stays as an addition in Workspace Trees. If the maintainer prefers #9's disabled state for direct attachments, only §6 changes.
2. **Usage refresh cadence.** [Usage and limit display](https://github.com/qodesmith/unimatrix-zero/issues/36) set an on-demand read every 5 minutes. The follow-up on [Reconnect, offline and error states](https://github.com/qodesmith/unimatrix-zero/issues/40) ruled out probe processes: never run `claude auth status` on a timer or start throwaway sessions to read status or usage. Reading: the periodic read runs only through what is already running (Codex's app-server for `account/rateLimits/read`; Claude's `get_usage` only on a warm session), and otherwise the display shows the last `rate_limit_event` with its age. No process is ever started to refresh a figure.
